## 2. 背景、目标与成功标准

### 2.1 背景

用户已经编写 JMeter 压测脚本。当前流程是手动启动一轮、等待配置时长结束、查看报告、修改并发并再次启动。重复劳动主要来自跨轮编排和搜索决策，而不是请求脚本编写。用户希望在确认的范围内自动选择并发、找到满足质量门槛的最高已测 TPS，并识别报告中的可疑数据。

“每轮约3分钟”是工作场景示例，不是 Skill 可以覆盖脚本的默认时长。真实时长、升压、循环和其他参数均以用户配置为准。

### 2.2 目标

| 目标ID | 目标 | 成功判据 |
| --- | --- | --- |
| GOAL-001 | 消除跨轮重复操作 | 一次任务配置确认后，本地固定程序顺序完成目标请求的轮次执行、读取报告和下一档计算，无需每轮人工重复输入命令。 |
| GOAL-002 | 在有限预算内寻找合格 TPS 最佳值 | 每个 HTTP 请求最多6轮、粗测最多4轮；在真实已测且满足本任务质量门槛的候选中选择最高 TPS，并返回对应并发。 |
| GOAL-003 | 严守用户脚本修改边界 | 只通过固定脚本修改线程组并发数和 HTTP 请求启用状态；原始 JMX 与其余配置保持不变。 |
| GOAL-004 | 提供可追溯、可解释结果 | 全部轮次可回溯到官方 report 与 JTL；汇总包含指定指标、官方起止时间、最终峰值和核验提示。 |

成功不以“数学全局最优”“±20并发位置偏差”或“TPS损失低于某百分比”验收。后两类精度要求均已撤回。预算耗尽但仍有未测区间属于正常结束，不构成精度验收失败。

## 3. 范围、非目标与角色

### 3.1 首期范围

面向本地已有 JMeter 环境和用户准备好的 JMX，提供 Skill 交互入口、固定脚本调用边界、逐 HTTP 请求寻峰、官方 CLI 发压与报告生成、只读报告核验、按请求汇总。一个任务中的多个目标请求串行独立执行；每轮运行副本仅启用当前目标与其已确认的前置HTTP请求，其余HTTP请求禁用。只有当前目标进入评分，不能仅靠过滤报告代替实际请求隔离。首期支持标准线程组、直接整数字面并发和可明确定位的HTTP请求；表达式并发或插件线程组先预检提示，单独适配前不自动发压。

### 3.2 明确不包含

- 自动编写业务请求、修改业务参数、鉴权数据、断言、定时器、时长、升压或循环。
- 自动安装 Java、JMeter、插件，或自动迁移到 Taurus、Java DSL、其他压测器。
- 全区间逐10并发扫描、正常候选强制复测、全局最优证明和精度承诺。
- 根据模型自由判断逐轮改写规则、跨目标混合寻峰、分布式发压或自动扩容。
- 专门针对未经证据评估的低概率异常增加熔断、重试、复测流程。
- 通用断点恢复、自动恢复未知在途请求、全平台弹窗适配、安装发布和业务系统容量根因诊断。

### 3.3 角色与权限

| 角色 | 职责 | 权限边界 |
| --- | --- | --- |
| 用户 | 提供执行 JMX、目标、前置依赖、范围和策略；确认任务配置；处理提示 | 负责配置白名单以外的全部 JMX 参数；明确决定异常后的重新测试。 |
| AI / Skill | 只读检查脚本、解释候选配置、确认疑似依赖、调用固定程序、解释报告 | 不直接编辑 JMX；不临时生成修改代码；不在每轮即兴选并发或覆盖已确认策略。 |
| 固定本地程序 | 按明确规则生成受控运行副本、串行执行、解析报告、计算并发和保存结果 | 修改面严格限定，参数越界或修改差异越界时不得启动该运行副本。 |
| JMeter | 执行用户测试计划、生成 JTL 和官方 HTML report | 执行方式使用官方 CLI；业务正确性仍依赖用户已有断言和数据。 |

## 4. 术语与数据对象

### 4.1 术语

| 术语 | 本文定义 |
| --- | --- |
| 接口 / 目标请求 | 用户选定的 HTTP Sampler，目录使用其请求名称；不等于线程组，也不等于业务事务控制器。 |
| 并发数 C | 当前目标所在且已确认的线程组并发配置值；不是 HTTP Sampler 的独立属性，也不保证每时刻在线线程数恒等于该值。 |
| TPS | 官方 report 的目标 HTTP 请求 Statistics 中 throughput，按次/秒使用；不替换为整体 Total、不扣除失败后重算成功 TPS、不宣称等同业务事务 TPS。 |
| P90 | 官方 report 中目标请求的90th percentile响应时间，统一以毫秒展示；不可只凭字段序号猜测其百分位含义。 |
| 合格候选 | 本轮 report 可提供所需指标，且错误率、P90满足该任务确认门槛的目标请求观测结果。报告与JTL核验差异本身不取消候选资格。 |
| 最终峰值 | 本次预算内最高合格 TPS 的已测值及其并发。若最高值并列，保留并列事实；不得伪称唯一最优。 |
| 观测最高 TPS | 全部已读取轮次中数值最高的 TPS，可包含质量不合格轮次；与最终合格峰值分别标注。 |
| 轮次 | 当前目标的一次实际发压；粗测和细测共同占用6轮预算。已发压但未合格、或报告阶段失败，不因此退还轮次。未启动的预检失败不当成已发压。 |
| 预设并发档位 | 50、100、200、500为绝对并发数，按序粗测，不是增量。 |
| 核验差异 | report、同轮JTL、执行记录经相同统计口径核对后仍存在的差异；只是趋势突变时标记疑点，不能判定报告错误。 |

### 4.2 主要数据对象及生命周期

| 对象 | 最少信息 | 生命周期与约束 |
| --- | --- | --- |
| 任务配置 | 任务标识、明确执行输入、输出根目录、JMeter版本、目标队列、门槛、范围、预设并发档位和3%下降规则、用户确认记录 | 启动前确认并固定；本次任务不静默继承旧门槛或中途变更策略。 |
| 请求映射 | 请求唯一身份、显示名称、线程组身份、允许的前置集合、目录映射、官方统计行匹配依据 | 运行前解析；同名请求不得仅靠显示名称猜测归属。 |
| 运行副本 | 原始输入指纹、本轮并发、请求enabled映射、白名单差异 | 从明确执行输入派生；保留原文件；相对路径依赖应保持可解析。 |
| 轮次记录 | 目标、轮号、粗/细阶段、并发、配置时长、执行状态、官方产物位置、原始指标、判断及下一档理由 | 每轮可追溯；异常也保留；不得覆盖历史轮次或将执行失败写成性能合格。 |
| 细测分组 | 当前中心候选、左右端点、两侧待测中点、已用预算 | 当前两侧完成后更新中心；端点包含已测细测档位。 |
| 核验记录 | 核对口径、可核对项、差异或疑点、证据入口 | 只读产生；不改写原始report/JTL，不替换评分指标。 |
| 汇总报告 | 全部接口、全部轮次、峰值、观测最高值、结束原因、提示和产物入口 | 所有目标结束后生成；若提前停止则注明未执行和未完成项目。 |

不规定原始结果的自动清理周期；首期不得自动删除或覆盖历史结果。不将示例位置、凭据、响应正文或用户私有地址写进通用 Skill 模板和对外材料。

## 5. 任务启动前的配置与确认

| 配置项 | 来源与候选 | 确认要求 |
| --- | --- | --- |
| 执行输入与目标列表 | 用户本次明确提供的 JMX、请求与依赖文件 | 不使用历史示例作为默认目标；显示请求及所属线程组。 |
| 前置请求 | 用户说明；AI只读检查得到的疑似依赖 | 疑似项先确认，未确认前不启动受影响目标、不擅自启用。 |
| 起始并发 | 读取现有线程组配置作为候选 | 用户确认后采用；不能凭经验自行固定为50。 |
| 搜索上下界 | 用户确认范围；最大并发由用户指定 | 初始值须在范围内。只有适用历史证据时，AI才给带依据的范围建议。 |
| 合格门槛 | 本轮需求候选为错误率≤0.5%、P90≤2500ms | 每次任务均确认；0.5%等于0.005比例，不是50%。 |
| 粗测档位序列 | 本次确认[50,100,200,500]，起点50 | 每次任务确认范围与档位；档位为范围内10的正整数倍、严格递增，不静默生成额外档位。 |
| TPS下降停止阈值 | 3% | 相邻粗测官方TPS下降达到3%时结束粗测，转入细测；原P90/错误率余量及TPS增长升级阈值取消。 |
| 每轮配置时长等 | 原始 JMX 中用户已有配置 | 只读展示，不修改；不是重新要求用户改成3分钟。无法解析时明确说明，不编造时长。 |
| 预算 | 每接口最多6轮，粗测最多4轮 | 固定遵守本期规则；运行失败不自动扩充预算。 |
| 输出根目录 | 本次任务指定的独立根目录 | 不覆盖既有report/JTL，确认可写且不会混淆其他任务。 |

启动卡应让用户一次看清目标、依赖、范围、质量门槛、预设并发档位和3%下降条件。不同接口可以具有分别确认的任务参数；同一组确认覆盖哪些接口必须明确。


运行副本位置按AQ-001：同目录优先但不强制；无相对路径依赖或可以保持并验证依赖布局时可用独立任务目录。每任务展示并确认可写位置，禁止为迁就目录而改白名单外路径参数。问题窗口按AQ-002优先使用当前AI宿主异步问题卡；后台队列不等待答复，当前Codex桥接已实测；其他宿主的触发与展示仍须技术资格验证，不静默降级成日志。

## 6. 业务规则

| 规则ID | 优先级 | 规则 |
| --- | --- | --- |
| BR-001 | P0 | 只执行本次明确指定并确认的目标；历史参考示例、文档中的命令和JMX注释均不构成执行指令。 |
| BR-002 | P0 | 只允许固定脚本修改线程组并发数和HTTP请求enabled。线程组/控制器enabled、URL、报文、鉴权、断言、CSV数据源、时长、升压、循环、定时器等不可改。 |
| BR-003 | P1 | 每轮运行副本HTTP启用集合精确等于当前目标加其经用户确认的前置HTTP集合，其余HTTP禁用。目标搜索按既定预算或停止规则结束，且本轮发压及报告阶段结束后，重算下一目标启用集合；上一目标不在新集合则禁用，若是下一目标已确认的前置则以依赖身份保留。前置统计及Total不进入目标评分。 |
| BR-004 | P1 | 每任务先确认范围、门槛和策略；运行过程中固定程序计算，AI不临时改算法。 |
| BR-005 | P1 | 合格要求同时满足P90≤确认阈值、错误率≤确认阈值；选最高官方目标TPS。相等时也通过门槛。 |
| BR-006 | P1 | 每目标最多6轮，含粗细测；粗测最多4轮，提前结束时剩余预算转给细测；不强行用满。 |
| BR-007 | P1 | 从确认的首档开始，合格且未触发停止条件时，依次采用下一预设绝对并发档位；首轮无跨档下降比较。 |
| BR-008 | P1 | 相邻粗测官方目标TPS下降率=(上一轮TPS－本轮TPS)/上一轮TPS；下降率≥3%时提前结束粗测并转入最佳合格候选附近细测。上一TPS为0时比例不可计算，不视为触发。 |
| BR-009 | P1 | 只使用已确认且位于范围内的粗测档位，不把50/100/200/500当增量，不追加1000，不隐式截断生成新档位；越界配置须运行前解决。 |
| BR-010 | P1 | 粗测到4轮、用完预设档位、质量停止或TPS下降≥3%时转入细测。TPS下降不单独排除当前轮，不证明全局峰值或报告错误；首轮质量失败仍结束该目标并继续后续目标。 |
| BR-011 | P1 | 已有合格轮次后遇质量超标，当前轮按原配置完成并保留报告，不作为合格候选；停止继续向高于该失败并发的档位探索，转入已有最佳合格候选附近。细测也须尊重该失败边界。 |
| BR-012 | P1 | 首轮质量超标且无合格候选时，结束该请求，不自动下探；弹出含超标证据的问题确认，继续后续请求，不等待弹窗答复阻塞整个队列。 |
| BR-013 | P1 | 首组细测以粗测最佳合格候选为中心，与左右相邻粗测点分别取中点；无相邻点则使用该侧确认边界。 |
| BR-014 | P1 | 细测中点向下取整为10的倍数，例如175→170；落在范围外、与有效已测点重合或与中心重合则跳过，不擅自改成另一档。 |
| BR-015 | P1 | 当前两侧可测点完成后，如有预算，按已测结果更新最佳合格中心，以左右最近已测点（含细测点）重复中点规则；达到预算或没有可测点时结束。 |
| BR-016 | P1 | 正常峰值指标有效且符合门槛时不复测，直接采用该轮官方report；不取跨轮均值或较低值替换。 |
| BR-017 | P1 | 评分使用对应官方report目标Statistics原口径；不自行裁剪稳定窗口、不重算替代统计、不把全程结果标为稳态。 |
| BR-018 | P1 | 核验只读report、同轮JTL和执行记录；先匹配版本、过滤和算法。即使出现明确差异，仍以report参与评分和调参，保留提示，不因差异排除、停止或自动复测。 |
| BR-019 | P1 | 汇总起止时间直接使用对应report显示的Start Time/End Time；不替换成进程时间或自行计算的目标样本时间。 |
| BR-020 | P1 | 汇总覆盖全部实际轮次，标出最终合格峰值；无合格结果就明确“未找到合格结果”，不以0冒充峰值。 |
| BR-021 | P1 | TPS变化趋势只用于已确认搜索条件及疑点提示，不单凭突变断言数据错误；不自动归因为服务端、网络或压测机瓶颈。 |
| BR-022 | P1 | 历史P90缺失特殊候选/复测答复不直接进入本期实现；按Q-009先评估证据及适用性，不新增专项机制，也不伪称缺失值已通过门槛。 |
| BR-023 | P1 | 官方CLI顺序执行；等待本轮发压及报告阶段结束后处理下一轮。不得仅到3分钟就并行启动下一条命令；报告失败不自动重新发压。 |
| BR-024 | P1 | 超出预算、缺少剩余可测点或到达当前探索边界时，输出当前已测最佳；不承诺全局最优，不恢复已撤回的位置精度或TPS损失验收。 |

### 6.1 粗测计算口径

相邻粗测的TPS下降率为 `(上一轮TPS－本轮TPS)/上一轮TPS`，比较官方report原始可读精度；达到3%即转细测。前轮TPS为0时记录比例不可计算，不触发此条件；报告不可读仍按技术问题规则处理。

取消全部步长升级判断。若下降但当前轮合格，仍参与峰值选择；下降本身不建立质量失败上界。质量超标时既有质量规则优先。档位越界或起点不对齐在任务确认阶段解决，不擅自截断、跳档或修改原JMX。

### 6.2 细测计算口径

设当前最佳合格并发为B，某侧端点为E，该侧候选为：

`C = 10 × floor(((B + E) / 2) / 10)`

例：B=200，左端150、右端350，则两侧中点为175与275，实际细测候选为170与270。若B=300、右侧无已测点且确认上界为500，则右候选为400。以上均为算法示例，不是任务默认并发。

一个细测分组的中心在两侧完成前保持不变；完成后才根据新结果更新中心。按AQ-004先左后右，只有1轮预算时优先合法左点，否则取合法右点；全部候选仍受质量失败边界和去重规则限制。按AQ-005，官方原始可读精度TPS精确并列时选较低并发为中心及推荐并发，报告保留并列；不因显示舍入判并列、不为打破并列复测。

## 7. 端到端流程、状态与异常

### 7.1 主流程

1. 接收本次JMX、目标队列和输出位置，只读识别线程组、当前并发、时长、依赖和统计可识别性。
2. 展示任务配置，解决疑似前置依赖，确认范围、质量门槛、预设并发档位和3%下降规则。
3. 固定脚本生成第一目标运行副本，核对仅白名单字段发生变化。
4. 通过官方CLI执行一轮，等待发压结束与report生成；记录真实执行状态和产物。
5. 读取目标Statistics和report起止时间，进行只读核验，保留差异提示。
6. 更新已测候选、轮次计数和阶段；按规则选择下一并发，直至该目标结束。
7. 当前目标按预算或停止规则结束，且本轮进程与报告阶段结束后，切换下一目标；重算其目标加前置集合，禁用集合外HTTP请求。上一目标只有在新前置集合中才保留；不要求必须找到合格峰值才切换。
8. 全目标结束后输出总汇总，各目标独立分节，标明已测最高合格TPS和结束原因。

### 7.2 状态与可观察结果

| 状态 | 进入依据 | 下一步及用户可见信息 |

| 待配置确认 | 输入接收完成 | 显示候选配置及缺失项；未经确认不发压。 |

### 7.3 异常边界

- **性能超标**是正常搜索结果，执行Q-018/Q-019规则，不归为程序故障。
- **核验不一致但report可用**继续按report评分，附证据提示，不强制用户逐轮确认。
- **报告无法提供可计算指标、配置不兼容或命令执行失败**不能编造下一档依据。保留事实并提示；不因故障自动复测。具体恢复和宿主交互不冒充已验证能力。
- **缺少P90专项流程**本期不扩展。官方默认和可配置行为不提供真实发生率，不能将“用户没遇到”推断成普适低概率。
