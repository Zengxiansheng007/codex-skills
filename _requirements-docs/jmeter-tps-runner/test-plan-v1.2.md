# jmeter-tps-runner 测试计划 v1.2

目标是证明固定修改边界、官方指标忠实性和有预算的独立寻峰，不以“找到了全局峰值”作为验收。本版在原风险策略上补入最终执行结论和明确证据类型。实际任务参数已确认且已完成，后续新任务仍需重新确认。

## 2. 测试层及独立验收

L1使用合成输入测试纯规则、XML白名单、报告读取器；不发请求。负例验证拒绝禁改字段和目标归属冲突，不只检查实现返回了true。

L2使用可控假进程/固定输出验证串行、预算、存储和报告失败路径；保留实际调用计数与时序。合成report明确标记fixture，不出现在真实汇总中。Windows参数探针必须验证子进程实际收到的argv，不能只检查字符串拼装。

L3在明确本次任务参数后使用用户JMX和实际JMeter，生成真实官方JTL及HTML。主机问题卡须实测：可以通过明确标为模拟的问题事件验证桥接，后台继续的进程记录单独保存；不能把测试问题描述成接口实际失败。

工程执行者提供测试及变更证据；Codex另行检查白名单/状态边界并运行相关测试，独立核对原报告与最终汇总。执行者completed/退出0不能替代验收。

## 3. 数据和环境

已验证环境：Windows、现有Python3.11/Java17/JMeter5.6.3，标准线程组及三个HTTP目标。原JMX由用户本次明确提供；只读保留，无用户JMX、地址、响应体或实际报告进入公开包。业务源文件和任务配置的证据仅本地保存。

实际配置：起点50，上限500，粗测50/100/200/500，错误率≤0.5%、P90≤2500ms，120秒/轮，最多6轮/目标；时长来自原JMX，不做修改。这是本次已确认任务记录，不是未来任务默认授权。

支持范围与局限见[架构](architecture-v1.3.md)及Skill的supported-inputs.md。测试预期不宣称覆盖未知插件、任意路径或所有JMeter版本。

## 4. 真实测试验收步骤（本次已执行；后续任务须重新确认）

1. 验证Java/JMeter实际版本、配置、报告百分位和CSV字段，检查路径依赖、标签唯一性及所有可执行节点。确认HTTP目标集合和前置集合。
2. 建立任务卡：起点/范围、质量阈值、3%下降条件、预设并发档位、最多6轮/粗测4轮、真实120秒、原件SHA、输出/副本路径和目标地址。用户已明确选择本任务50，并非自动对齐。
3. 固定程序生成第一轮副本；独立核验除目标线程组并发及HTTP enabled外的差异为空。验证全部HTTP启用集合精确相等。
4. 通过官方 `jmeter -n -t <copy> -l <jtl> -e -o <report>` 执行，等待真实进程与报告阶段结束。不要仅按120秒定时启动下一轮。
5. 读取目标Statistics的样本数/P90/TPS/错误率及report Start/End Time；记录来源文件、字段和单位。JTL核验只追加提示，仍依report质量评分并选择下一档。
6. 每目标独立计数，按预算/质量/合法点终止，切换HTTP集合。首轮失败结束该目标、投递异步问题卡并继续下一目标。正常不复测，也不为了覆盖未发生分支追加真实轮次。
7. 全部结束后逐接口逐轮核对六列、原report链接及最高合格TPS。前后原件SHA相等，实际发压不超过每目标6轮。报告未生成时明确技术失败，不以零填补。

若3个接口都用满6轮，配置时长累计为36分钟，另有JMeter启动/退出、报告生成等开销；这不是完成时限，也不构成增加轮次的授权。

## 5. 测试门禁和回归范围

进入真实测试必须先通过L1/L2的修改白名单、参数边界、串行预算和报告映射关键项，并补齐本次任务确认。每个开发任务仅运行新模块及关联模块测试；跨模块契约变更才扩大回归。无新变更/失败/风险时复用已绑定哈希的证据，不重复跑全量。

发现实现缺陷时停止安排新发压并修对应模块；不能重放未知在途业务。独立修复验证通过后，任何重跑业务请求都须明确剩余预算与任务关系，禁止以“测试代码”为名规避六轮限制。

退出条件：AC-001～026有真实或明确标注的模拟证据，TQ-001～004分别有结论，代码/包检查和秘密扫描通过，实际授权目标的CLI及report生成被验证，所有原件不变，未解决P0/P1为零。若用户未补齐参数或环境不兼容，保留未完成项；不能宣称真实测试或整体Skill已完成。


## 6. CQ-001新增断言

1000→970触发，1000→970.01不触发；用相邻粗测而非历史最高比较；零TPS不除零；预设为50/100/200/500而非400；质量失败优先；合格下降轮不排除；下降不建立质量失败上界；粗测提前结束剩余预算用于原两侧中点细测。没有单凭3%下降判定数据异常。
