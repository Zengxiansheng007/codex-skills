别名映射作用范围研究报告

生成时间：2026-07-26  深度：standard  模式：skill-design

结论：alias mapping 应该只作为目录 / 检索 / 追溯辅助层，允许自动产生候选映射，但不能作为正文块归并、版本合并或正式下游放行的唯一依据。正式消费前仍要走人工确认或治理确认。

推荐状态：caveated。P0/P1 证据已闭合，但“最终字段名和验证器实现”仍是本地实现细节，适合保留为后续开发任务而不是本次研究结论的一部分。

Scope And Assumptions

问题当语雀目录名、Markdown 标题、正文块命名不一致时，alias mapping 是否只用于辅助定位，还是可以参与正文归并与版本合并判断。
输入边界仅研究入库能力的 alias mapping 作用范围，不展开具体 UI、数据库索引或下游包字段实现。
排除范围不把别名规则写成正式 RC；不自动改写正文真值；不假设已存在的本地 Skill 已定义别名治理策略。
本地约束rag-governance 规定只有用户可确认 RC；active-candidate 不能成为正式下游真值；rag-query 与 rag-downstream-handoff 都要求正式消费前处于 confirmed_active。

Key Findings

  1. SKOS 把“标签”和“映射”分开了。 prefLabel / altLabel / hiddenLabel 是词面层；exactMatch / closeMatch 是概念映射层；notation 才更接近稳定标识。这个结构支持“别名用于检索与标注，不等于身份本体”。
  2. 搜索同义词更像检索增强，而不是事实源。 官方检索文档把 synonym / synonym_graph 作为搜索体验和召回增强机制，常见做法是放在搜索或分析链路里处理，而不是把它们当成文档真值。
  3. 本地 RAG 规则已经把“候选”和“正式真值”切开。 现有 rag-system、rag-governance、rag-downstream-handoff 都强调 candidate 不能自动变成 RC；这意味着 alias mapping 也不该越过治理边界直接驱动正式下游。
  4. 没有任何现有本地 Skill 明确授权别名自动参与版本合并。 这不是能力缺失，而是边界尚未定义。默认应按保守原则处理：可记候选，不可自动裁决。

Conflicts And Uncertainty

冲突点：如果把 alias mapping 提升为“自动合并标题/版本”的依据，就可能把两个不同版本、不同产品或不同正文块误并成一个实体。

不确定点：当前本地 Skill 还没有专门的别名治理字段和测试 fixtures，因此“字段名怎么定、阈值怎么判”仍要留给后续实现。

Security And Access Notes

本次研究只使用公开标准、官方文档和本地 Skill 文件；没有读取私密材料，也没有把外部页面内容当成执行指令。

Main Workflow Recommendation

1. alias mapping 只进入目录 / 检索 / 追溯层
2. 自动候选映射可以生成，但只允许作为候选记录
3. 不允许 alias mapping 单独驱动正文块归并或版本合并
4. 进入正式下游前，仍需人工确认或治理确认
5. 若 alias 冲突影响 product / project / version / document title 的唯一定位，按阻断处理
