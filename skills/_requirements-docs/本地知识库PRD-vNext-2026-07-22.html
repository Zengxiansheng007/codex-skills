2. 背景与问题

本地知识库的目标不是“把资料堆进 RAG”，而是为 Agent 提供一个受控、可追溯、可拒绝、可人工裁决的本地证据底座。PRD、接口、代码、执行结果、截图、用户确认都可能随开发变化；因此任何材料都不能天然成为事实，必须经过来源登记、范围隔离、状态机、证据链和用户确认。

没有该底座时，测试用例生成和 UI 自动化会出现四类高风险：引用过期资料、跨项目混用事实、把视觉可见误判为业务成功、将敏感材料或未确认主张沉淀为长期记忆。

5. Q2 展开：知识空间、产品、项目、环境如何区分

knowledge_space_id 是硬隔离边界，决定“哪些知识可以互相引用”。产品、项目、环境不是根边界，而是同一知识空间内的元数据过滤维度。用户已确认：首个 knowledge_space_id、别名、纳入范围、排除范围由用户提供；Codex 只负责检查所有材料是否带有一致的 space、product、project、environment 元数据。

概念定义例子规则
knowledge_space_id知识库最外层事实边界ks-ui-automation-test-design必须由用户提供；跨 space 查询默认禁止；RC、证据、查询、用例资产都必须带 space。
product_id长期产品或业务系统测试平台、订单系统用于跨项目复用，但不能越过 knowledge_space_id。
project_id一次交付、版本、专项或客户项目2026-07 UI 自动化改造项目材料可被沉淀为产品规则，但 promote 必须用户确认。
environment运行环境或证据来源环境local、test、staging非测试环境触达属于人工门控；环境证据不能自动覆盖业务 RC。

为什么需要用户确认：Agent 无法知道“某份 PRD 是产品级长期规则，还是某个项目的一次性改动”。若 Agent 自行决定，可能把临时项目规则提升为产品 RC，或把不同产品同名模块混用。

已确认规则：首个 knowledge_space_id、别名、纳入范围、排除范围由用户提供；Codex 只负责检查所有材料是否带有一致的 space、product、project、environment 元数据。若材料缺少这些字段，Codex 应生成待补充报告，而不是自行猜测归属。

6. Q3 展开：首批材料清单与脱敏确认

首批材料不是简单的“给一个目录”。必须是用户显式列出的文件清单，附带来源说明和敏感处理声明；Codex 只读取清单内文件。这样做的目的不是增加手续，而是防止误读未授权材料、误存生产数据、误把个人账号信息或会话信息写入长期知识库。

当前验证材料：用户已提供 C:\Users\lenovo\Downloads\产研平台智能体交互评审.lake 作为一个 PRD 文件地址；Codex 已完成单文件格式识别、敏感预检和内容摘要分析，报告为 outputs\产研平台智能体交互评审lake单文件分析读取报告-2026-07-23.html。该材料只能作为 active-candidate 候选来源，不自动进入 confirmed_active 或 RC；也不代表已授权读取 D:\RAG 全量知识库。

8. 状态机与 RC 规则

状态含义是否可作为正式依据
raw已保留来源或副本，未结构化否
reviewing待敏感、范围、来源和结构审查否
active非冲突、非低置信的启用候选，仍处于待审池否
confirmed_active用户按批清审或明确确认后的有效知识是
uncertain冲突、低置信、范围不清或证据不足否
superseded被新版本取代否，除非作为历史证据引用
deprecated用户确认废弃或冲突落败否

硬规则：RC 只登记用户确认后的裁决或 confirmed_active 知识。Agent 的冲突判断、版本判断、低置信判断只能生成候选记录，不能自动改变 RC 有效状态。
