WorkBuddy 方案优点

  • 吸收用户裁决及时：方案已将权威模型从“固定来源排序”修正为“有效性门控 + 人工治理三规则”，契合“PRD 也可能过期”的关键修正。
  • Agent 可用性强：目录采用 00_inbox/01_raw/02_structured/03_evidence/04_test_assets/05_skill_ref/06_governance/07_handover/08_cache，读写路径直观，适合 Codex 消费。
  • 安全边界清楚：明确禁凭据、禁未脱敏生产数据、禁自动扫描其他磁盘、第三方 Skill 只吸收机制。
  • 状态机更贴近治理：confirmed_active 把“已启用但未批清”和“可供用例生成”区分开，避免 Agent 误用待审内容。
  • 测试知识沉淀比 Codex v1 更展开：增加 Payload、GoldenCase、stable_trace_id、oracle_type、Playwright + Solution D 证据链等内容。

WorkBuddy 方案缺点

  • 原文件仍有已过期 open item：O-004 已被用户确认关闭，但 PRD v1.1 仍列为 P1。
  • 内部方案容易被误读为已核验：qa-skill / test-case-xlsx-generator / Solution D 只能登记为“用户后续提供后复核”的实施门禁，不能作为当前 RC。
  • 部分参考资料权威度不足：博客和厂商实践可以启发，但不能支撑 P0/P1 结论。应把它们放在“机制启发”层，而不是“高置信依据”层。
  • 目录模型与对象模型需要合并说明：WorkBuddy 的目录结构适合落地，Codex 的 SRC/EVD/CLM/RC 对象模型适合契约；两者需要一张映射表。
