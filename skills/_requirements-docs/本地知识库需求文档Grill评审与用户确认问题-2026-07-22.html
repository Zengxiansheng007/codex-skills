三、主要缺口与修正方向

P0-GR-01 同步授权边界已转为实施授权边界

问题：用户已确认生成新的 PRD、开发计划、测试计划三份独立草案，因此“是否生成 vNext 文档”不再阻塞；但真实写入 D:\RAG、创建 .codex/skills/rag-system 或同步到其他总需求文档仍需单独授权。

建议：把当前三份 vNext 文档冻结为草案基线；实施前再逐项确认写入路径、Skill 创建范围和首批材料清单。

P0-GR-02 首个知识空间边界未落定

问题：方案已经强调项目、产品、环境边界，但首个 knowledge_space_id 的命名、范围、排除项仍需用户裁定。没有硬边界，跨项目污染测试无法定义。

建议：把 knowledge_space_id 定为强制根边界；产品、项目、环境作为元数据过滤维度。首个 ID、别名、范围说明、排除目录均由用户确认。

P0-GR-03 第一批材料清单与脱敏证明未给出

问题：本地知识库的第一批材料必须来自用户显式提供，且需要用户确认已脱敏。没有清单就不能设计真实入库验收，也不能判断哪些内容允许进入待审池。

建议：用户提供第一批候选材料清单、来源说明、敏感信息处理声明；Codex 仅做文件级读取和结构化评审，不自动扫描其他磁盘。

P1-GR-04 active 与 confirmed_active 容易混淆

问题：用户已确认“后者才登记为 RC”。若文档中仍让 Agent 把 active 当成正式依据，会造成误用。

建议：统一定义：active 只表示当前待审或可见材料状态；正式测试设计、PRD 挖掘和自动化引用只能使用 confirmed_active 的 RC。

P1-GR-05 内部 Skill 与 Solution D 证据链仍是本地约束

问题：外部资料能补强方法论，但无法证明本地 ui-test、auto-testcase-generator、Solution D 的真实接口和产物格式。

建议：在开发计划中把内部 Skill 读取、样例输入输出、失败归因报告和证据字段校验列为前置任务；未核验前不得把接口细节写死为 RC。

P1-GR-06 检索后端上线门槛需要量化

问题：SQLite FTS5、向量索引和缓存层都有价值，但若在 MVP 直接引入，会增加维护复杂度和调试成本。

建议：MVP 先使用 INDEX.md、frontmatter、manifest 和证据 JSON；当语料规模、黄金查询失败率或人工查找成本达到阈值后，再引入 SQLite FTS5；向量索引放在更后阶段。
