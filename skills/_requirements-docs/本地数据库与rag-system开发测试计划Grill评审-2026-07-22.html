本地数据库与 rag-system 开发测试计划 Grill 评审

评审对象：本地数据库与 rag-system Skill 开发计划、本地知识库开发计划、本地知识库测试计划。

评审路线：design-review 为主，pre-implementation 与 test-case-design 为辅。

结论：开发方向成立，但测试计划需要补齐 rag-system Skill 自身的测试面；真实执行仍受用户授权和首批输入阻塞。

1. 总体判断

维度评审结论级别
架构方向“本地数据库数据层 + rag-system 根 Skill + 子 Skill”的拆分合理，能避免巨型 Skill 和检索结果直接变事实。通过
安全边界计划明确禁止自动扫描磁盘、敏感材料入库、自动 RC、直接执行下游测试，边界符合用户确认。通过
开发可执行性阶段顺序合理；用户已说明 D:\RAG 文件已存在，但真实实施前仍缺少检查/使用该路径、创建 Skill 目录、首个 space 和材料清单授权。P0 阻塞实施
测试充分性测试计划覆盖数据层治理，但没有把 rag-system 根 Skill 和子 Skill 契约作为一等测试对象。P1 缺口
下游契约Evidence Packet、RC Packet、Change Impact Packet、Test Asset Manifest、Solution D Evidence Contract 已预留，但字段级 JSON Schema 和失败样例还不够具体。P1 缺口

2. 主要优点

  1. 事实源与缓存分离：开发计划坚持 INDEX.md、frontmatter、manifest、证据 JSON 为 MVP 真值，08_cache 可删除重建，降低早期架构复杂度。
  2. RC 门禁清楚：active 只代表待审，confirmed_active 才能作为正式 RC，能防止 PRD 或历史材料被误当绝对事实。
  3. 上下游边界克制：rag-system 输出只读包，不执行 ui-test、不生成正式测试用例、不绕过用户审批。
  4. 阶段顺序稳：先治理、schema、状态机、证据包，再考虑 SQLite FTS5 和向量检索，符合当前 MVP 风险优先级。

3. 缺陷与优化点

ID问题影响建议级别
F-001测试计划仍以“本地知识库数据层”为中心，未单列 rag-system Skill 测试矩阵。后续即使数据层测试通过，也不能证明根 Skill 会正确路由、拒绝、渐进加载、调用子 Skill 或聚合 Evidence Packet。新增 TC-RAG-SKILL-001..008：触发识别、space 检查、子 Skill 路由、越权拒绝、提示注入拒绝、下游 handoff、错误聚合、forward-test。P1
F-002下游契约只有字段名，缺少字段级 JSON Schema、正反例 fixture、版本号和兼容性规则。auto-testcase-generator、ui-test、Solution D 可能各自解释字段，导致集成返工或错误消费 active/uncertain。为五类包建立 schema_version、必填字段、状态枚举、失败包样例和只读约束。P1
F-003开发计划列出子 Skill，但未定义每个子 Skill 的最小文件结构和验证命令。后续创建 Skill 时可能膨胀成教程型文档，或缺少引用资源、脚本和 forward-test。每个 MVP 子 Skill 明确 SKILL.md、references/、scripts/、fixtures、拒绝条件和质量校验命令。P1
F-004SQLite FTS5 引入阈值仍是定性描述。不会阻塞 MVP，但后续可能围绕“什么时候该升级检索”反复争论。首批语料跑完后，把阈值登记为可调参数，如黄金查询失败率、人工查找分钟数、语料条目量。P2
F-005测试计划没有显式写出“测试计划自身版本变更后如何回归 rag-system Skill”。计划迭代时容易只回归数据层，遗漏 Skill 触发描述、路由和下游包兼容性。新增计划变更回归：Skill 触发、子 Skill 路由、packet schema、拒绝条件、黄金查询全量回归。P2
