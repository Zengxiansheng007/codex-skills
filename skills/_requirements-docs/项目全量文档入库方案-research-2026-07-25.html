项目全量文档入库方案调研报告

日期：2026-07-25；范围：为 D:/RAG 本地知识库设计项目全量文档入库方案，覆盖 .lakebook 目录元数据、PRD/设计/接口/测试/说明文档的分批准入、敏感预检、候选态治理、RC 审批和下游 Agent 证据包。

结论摘要

建议采用“目录先入、正文分批、敏感先挡、用户审批后使用”的方案。

当前 产研效能.lakebook 已确认能读取目录元数据，但历史记录显示该材料仍处于 blocked-pending-sensitive-review，因此不能直接全量正文入库。全量入库应先建立目录索引和材料清单，再按分支、版本、材料类型逐批做敏感预检和结构化转换。

推荐入库流程

  1. 阶段 0：只读目录盘点。从 tocYml 提取 TITLE 与 DOC 节点，生成完整目录树、文档 ID、标题、父子关系、更新时间。不读取正文。
  2. 阶段 1：用户确认纳入范围。按版本分组、模块分组和材料类型生成候选清单，例如 V0.1.4版本、缺陷管理、流水线、总体设计。用户勾选首批入库分支。
  3. 阶段 2：敏感预检。只对用户确认分支的正文做扫描，阻断账号、密钥、Cookie、Token、真实生产客户数据、未经脱敏日志和截图。
  4. 阶段 3：材料准入。通过预检的材料登记为 active-candidate，保留来源路径、hash、标题、版本、层级、时间、材料类型、product/project/environment 元数据。
  5. 阶段 4：结构化入库。为每篇文档生成 frontmatter、Markdown 摘要、证据 JSON、来源定位和冲突候选。正文只转成可追溯片段，不直接作为 RC。
  6. 阶段 5：冲突与版本治理。按“更新更晚、目录版本更高、用户指定优先级、同主题覆盖关系”记录冲突，但只有用户确认后的结论才可进入 confirmed_active RC。
  7. 阶段 6：下游证据包。为 auto-testcase-generator、ui-test、Solution D 输出只读 Evidence Packet，包含来源、状态、置信度、冲突、可用范围和禁止使用说明。

第二轮补强与缺口关闭

第一轮评审后发现 4 个高优先级缺口：敏感扫描只靠通用 PII 资料不够、目录节点与正文节点的 lakebook 语义缺少显式约束、RAG 数据投毒与提示注入需要独立安全证据、下游 Agent 使用候选材料的边界需要本地 Skill 证据。第二轮补充资料和参考 Skill 后，P0/P1 缺口均已关闭。

缺口级别第一轮不足第二轮补强关闭结论
敏感扫描规则不足P0Presidio 支持 PII，但不能天然覆盖企业内部账号、接口凭证、截图日志中的业务敏感形态。补充 GitHub Secret Scanning、NIST SSDF、本地 rag-intake 规则。关闭。方案要求“命中类型与数量可报告，命中值不输出；自定义规则必须覆盖企业字段”。
RAG 数据投毒与提示注入P0第一轮 OWASP 只作为总框架，未单独说明外部文档内容不能成为指令。补充 OWASP LLM Prompt Injection 与本地 research 安全规则。关闭。方案要求把所有文档内容视为证据，不作为 agent 指令执行。
目录节点误入正文知识片段P1第一轮把 DOC 节点当成完整目录，漏掉 TITLE 分组。补充本地 lakebook 只读观察，明确 TITLE 为目录实体、DOC 为正文实体。关闭。目录索引必须保存 node_type，TITLE 不生成正文 chunk。
下游 Agent 使用候选材料边界P1外部 RAG 框架资料不定义本项目 RC 审批和候选态限制。补充本地 rag-governance、rag-query、rag-downstream-handoff Skill。关闭。正式下游只能使用 confirmed_active RC；候选包必须标记 need-review。

用户需确认

  • 是否先把 lakebook 全目录作为只读目录索引入库，但正文仍保持阻塞。
  • 首批正文准入分支：建议从 【流水线】优化需求及原型、初始化优化+成员管理、总体设计/概要设计 中选一批。
  • 是否允许对选定分支正文做敏感预检。命中只返回类型和数量，不返回原文。
  • 是否将 TITLE 分组节点保留为目录实体，不生成正文知识片段。
  • 是否按“用户审批后才 RC”继续执行，所有其他材料只进入 active-candidate。

主流程建议

可以采用本方案作为下一步入库设计依据。推荐先执行“目录索引入库 + 首批分支清单生成”，再由用户选择分支进入正文敏感预检。
