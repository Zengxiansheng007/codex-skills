测试用例编写完整流程与需求文档

文档 ID：PRD-TCD-002｜版本：v2.0｜日期：2026-07-15｜状态：review-ready｜类型：test-case-design-governance-prd

目标：把 PRD、设计、代码、运行证据和用户说明中的“来源主张”，经过检索、澄清、用户确认、领域建模和测试预言机设计，转化为可追溯的正式测试用例，并继续连接 UI 自动化执行与证据反馈。任何来源都不是永久真值；只有适用范围明确且由用户确认的 RC 才能支撑正式用例。

1. 文档边界

目标读者需求分析 Agent、测试设计 Agent、测试人员、UI 自动化 Agent、最终裁决用户。
基线来源现有《测试用例设计需求文档》v1.0、《测试用例设计完整流程与治理实施计划》v1.0、知识库 Grill 已确认决策、测试与 UI 自动化参考资料调研评审。
包含来源治理、知识检索、需求挖掘、Grill、规则确认、领域模型、测试点与用例、统一模型、多格式输出、自动化候选、执行反馈、变更与根因治理。
不包含具体项目的详细测试用例、浏览器脚本、生产执行、凭据配置、知识库实际部署、第三方框架安装。
下游交接auto-testcase-generator 负责生成/维护用例；ui-test 负责探索、确定性验证、证据和执行质量报告。
命名纠正：旧文档曾把 RC 同时用于规则裁决和根因族，存在歧义。自本版起，RC 仅表示用户确认规则（Rule Confirmation）；失败根因统一使用 RCA。旧数据迁移时必须显式映射，禁止按字段名猜测。

2. 核心对象与可信模型

对象含义最低要求
SRC版本化来源文件或运行来源唯一 ID、hash、类型、版本/时间、范围、状态、原始定位。
EVD可定位证据片段关联 SRC、章节/页面/DOM/API 定位、原文片段、提取批次。
CLM从来源提取的主张主张内容、适用范围、支持/冲突证据、状态；不得自动视为事实。
RC用户明确提出或确认的规则规则内容、适用知识空间/版本/环境、来源主张、确认时间、状态与关系。
MOD/OBJ/STATE模块、业务对象和状态模型唯一 ID、定义、关系、来源与未决项。
TP/TC测试点与测试用例追溯 RC、预言机、前置、数据、步骤、预期、风险和状态。
CHG/IMP来源变化与候选影响新旧版本、语义差异、受影响对象、证据、人工处理状态。
RUN/EVD执行记录与执行证据环境、构建、步骤、结果、截图/trace/API/下游证据。
ISS/RCA问题与根因族问题状态、严重度、阻断对象、根因证据、重复次数和纠正动作。

可信原则：SRC → EVD → CLM 只证明“某来源表达过什么”；RC 才证明“用户确认当前应按什么规则测试”。PRD、设计、代码、页面行为和接口响应可以互相支持或冲突，但 Agent 不得以固定排名自动裁决。

3. 完整编写流程与门禁

门禁活动产物通过条件失败去向
G0 输入准入接收用户明确指定的需求、设计、代码、页面、接口和既有用例。SRC 候选清单授权、范围、版本、敏感性和可访问性已记录。拒绝或请求补充，不继续解析。
G1 来源基线计算版本/hash，登记范围和新旧关系候选；不强制来源总排名。SRC、EVD、CLM每项主张可回到原始位置；冲突和过期均显式标记。ISS-SOURCE。
G2 知识检索按 knowledge_space_id 检索适用 RC 和证据。Evidence Packet返回引用、版本、范围、命中状态、冲突和查询轨迹。unknown/conflict/need-review。
G3 需求挖掘识别模块、对象、角色、状态、业务规则、数据约束、接口、异步和下游。模块理解、CLM、缺口清单关键流程、异常、边界和未决问题均有 ID。ISS-MINING。
G4 Grill 与裁决逐项挑战矛盾、模糊、不可测或高风险主张，由用户确认规则。RC、ISS 更新P0 问题已关闭；RC 的内容、范围和关系由用户明确确认。保留候选测试点，禁止正式用例。
G5 设计就绪检查规则、范围、角色、状态、上下游、预言机和证据入口。Readiness Report正式用例所需 RC 齐备，无冲突阻断。打回对应根因阶段。
G6 领域建模形成术语、对象、状态机、权限、业务 ID 和上下游模型。MOD/OBJ/STATE 模型模型与 RC 双向追溯；未知项不被模型补写。ISS-DOMAIN。
G7 测试设计按规则和风险生成测试点，选择预言机，组合正常、异常、边界、权限、状态与恢复场景。TP、候选 TC每个关键 RC 至少有正向与必要反向覆盖；每个预期可观察。ISS-DESIGN。
G8 统一用例模型把用例写入单一结构化模型，再生成 Markdown、HTML、JSON。TC ModelID、追溯、步骤、预期、数据和状态一致；无孤立项。ISS-SCHEMA/TRACE。
G9 输出一致性校验三种输出内容、数量、ID 和追溯关系。渲染件与验证报告三种输出来自同一模型且差异为零。重新渲染，禁止手工分别修改。
G10 自动化候选评估稳定入口、确定性预言机、数据可控、证据可得和写操作风险。Automation Candidate满足候选门槛并标明 Playwright/Hybrid 方向。保留手工用例。
G11 执行移交将用例、定位线索、业务 ID、网络/任务/下游校验点交给 ui-test。Explore Steps / Execution Contract视觉探索与确定性验证职责分开，证据要求完整。ISS-HANDOFF。
G12 反馈闭环汇总 RUN/EVD/ISS，区分产品失败、环境失败、脚本失败和 Agent 失败。报告、RCA、CHG/IMP失败有证据、归因和回流对象；重复根因触发升级。打回来源、RC、模型、用例或执行层。

4. 测试预言机与用例结构

4.1 预言机分类

类别验证对象典型证据
业务规则是否符合适用 RC规则 ID、计算结果、状态变化。
权限与数据范围角色能否看见/操作正确数据菜单、按钮、接口状态、数据集合差异。
状态机迁移、拒绝、回退、幂等迁移前后状态、事件、审计记录。
数据契约字段、格式、边界、持久化UI、API、数据库允许的只读证据。
异步与下游任务、事件、下游业务结果任务状态、业务 ID、网络响应、下游页面/API。
视觉与交互页面可见状态和操作反馈截图、DOM、可访问性树；不得单独证明下游成功。
恢复与安全失败回滚、重试、重复提交和危险写操作状态不变/恢复、审计、明确的安全边界。

4.2 正式用例必填字段

test_case_id、标题、目标、优先级、适用范围、前置条件、测试数据、步骤、逐步预期、最终预言机、RC 追溯、来源证据、清理/恢复、自动化适配、状态、变更记录。缺少适用 RC 时只能标记为 candidate，不得标记为 formal。

5. 功能需求

ID需求验证方式
FR-TCD-001系统必须建立版本化来源基线，保留定位、范围、状态和冲突，不实施固定真值排名。变更来源后仍可查询旧版本和差异。
FR-TCD-002知识检索必须返回 Evidence Packet，包括 RC、引用、版本、范围、冲突和查询轨迹。结构校验与五类真实查询。
FR-TCD-003需求挖掘必须覆盖模块、对象、角色、状态、规则、数据、接口、异步、下游和未知项。挖掘清单与孤立项检查。
FR-TCD-004只有用户明确提出或确认的规则可登记为 RC；Agent 只能提出候选关系。无用户确认时状态保持 candidate。
FR-TCD-005无适用 RC、RC 冲突或 P0 未关闭时，不得生成或更新正式用例。门禁负向测试。
FR-TCD-006领域模型、测试点和用例必须双向追溯到 RC 与证据。RTM 与孤立项验证。
FR-TCD-007测试设计必须显式选择预言机，覆盖正常、异常、边界、权限、状态、异步和恢复风险。覆盖与预言机审查。
FR-TCD-008HTML、Markdown、JSON 必须由同一模型生成，并保持 ID、内容和数量一致。跨输出差异校验。
FR-TCD-009来源变化必须先生成 CHG 和候选 IMP，不得自动改写 RC 或正式用例。增量变更回归。
FR-TCD-010自动化候选必须有稳定入口、确定性预言机、可控数据、证据入口和安全边界。候选门槛校验。
FR-TCD-011执行反馈必须区分产品、需求、数据、环境、脚本、工具和 Agent 根因。RCA 分类样例与回流检查。
FR-TCD-012相同 RCA 第二次出现时必须升级治理问题并要求系统性纠正。重复失败模拟。

6. 业务规则与非功能需求

ID规则
BR-TCD-001检索命中不等于事实；只有范围匹配且状态有效的 RC 可支撑正式测试预期。
BR-TCD-002新旧关系限于 supersedes、coexists_with、withdrawn_by、corrected_by、conflicts_with；用户确认后才生效。
BR-TCD-003页面提示、Toast 或按钮变化不能单独证明 API、异步任务和下游业务成功。
BR-TCD-004不得为了让执行通过而弱化断言、删除高风险场景或静默修改预期。
BR-TCD-005问题 ID 在打回和重做中保持不变；状态按 open、clarifying、decided、verified、closed 流转。
ID非功能要求目标
NFR-TCD-001可追溯性正式用例到 RC、证据和执行结果的关键链路覆盖率 100%。
NFR-TCD-002可审计性用户确认、状态变化、自动生成与人工修改均留痕。
NFR-TCD-003一致性三种输出来自同一模型，稳定 ID 不因排序或措辞变化而重建。
NFR-TCD-004安全不得持久化账号、Cookie、Token、密钥或未脱敏生产数据。
NFR-TCD-005可靠性失败必须可定位到门禁和对象；验证器失败时不得宣称完成。

7. 验收标准、DoR 与 DoD

IDGiven / When / Then
AC-TCD-001Given 两份来源表述冲突，When 建立基线，Then 两个 CLM 均保留且系统不自动选择真值。
AC-TCD-002Given 用户未确认规则，When Agent 生成测试内容，Then 只能输出带引用候选测试点，不能输出正式 TC。
AC-TCD-003Given 用户确认 RC，When 通过 G5-G8，Then 每个正式 TC 可追溯到适用 RC 和 EVD。
AC-TCD-004Given 来源 hash 变化，When 重新导入，Then 新建 SRC/CHG/IMP，既有 RC 和正式 TC 不被自动修改。
AC-TCD-005Given 同一统一模型，When 渲染三种格式，Then TC 数量、ID、预期和追溯一致。
AC-TCD-006Given 页面显示提交成功但 API/任务失败，When 执行，Then 用例不得判定业务成功。
AC-TCD-007Given 同类 RCA 第二次出现，When 关闭问题，Then 系统阻止普通关闭并创建升级项。
AC-TCD-008Given 自动化候选缺少确定性证据，When 评审，Then 保留手工用例并标记不可自动化原因。

DoR：已确定 knowledge_space_id、目标模块、版本/环境、授权来源、用户确认入口、关键业务 ID、风险边界；P0 未决项为零。

DoD：G0-G12 产物可审计；正式用例追溯完整；三种输出一致；变更不静默覆盖；自动化移交含确定性证据；验证报告无 P0/P1/P2 结构问题。
