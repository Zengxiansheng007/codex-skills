别名治理规则具体设计研究报告

生成时间：2026-07-27  深度：standard  模式：skill-design / plan-support

结论：别名治理不应嵌在正文结构里，而应作为一个独立的、版本化的治理注册表（alias_registry）运行；它只负责目录 / 检索 / 追溯辅助，不负责正文真值、RC、或正式下游放行。正式裁决仍归 rag-governance，正式下游仍只认 confirmed_active。

推荐状态：caveated。P0/P1 证据已闭合；未闭合部分主要是实现级字段名、阈值数值、以及后续存储引擎选型，属于本地实现细节，不影响本次规则设计结论。

Scope And Assumptions

研究对象新 rag-structure-fidelity / 别名治理层的具体规则设计：候选生成、人工审批、历史保留、作用域隔离、重评触发、与正文结构/RC/下游边界的关系。
明确边界alias mapping 只作为目录 / 检索 / 追溯辅助层；可自动生成候选，但不能作为正文块归并、版本合并、RC 生成或正式下游放行的唯一依据。
已确认前提第一版只强制文档级候选，区块级仅覆盖关键语义块；关键定位冲突必须阻断，普通冲突默认 need-review；候选草稿分层，审批记录保留历史；新审批可覆盖当前生效结论，但旧记录必须保留；同作用域重评先增量、必要时全量。
排除范围不创建真实 D:/RAG 记录，不执行任何下游测试，不定义具体数据库 DDL，不给出最终阈值数值，仅给出规则形状与状态机。

Key Findings

  1. SKOS 把词面标签和概念映射分开了。 skos:prefLabel、skos:altLabel、skos:hiddenLabel 是 lexical labels；skos:exactMatch、skos:closeMatch 是 mapping properties。也就是说，别名/同义词更适合做“显示/检索/辅助定位”，而不是直接升格为身份真值。
  2. 搜索同义词是检索增强，不是事实源。 Elastic 官方文档把 synonyms 作为 search / indexing 的分析配置来管理，并明确可在 search time 或 index time 使用；这支持把别名做成“可重载的派生检索层”，而不是把它当作源数据真相。
  3. PROV 模型适合承载别名治理的审计链。 PROV 关注 entities、activities 和 people，目标是支撑对质量、可靠性、可信度的评估，因此适合记录别名候选由谁、何时、基于什么规则生成与审批。
  4. 本地 RAG 规则已经把候选与正式真值切开。 rag-system、rag-governance、rag-downstream-handoff 都明确：candidate 不能自动成为 formal downstream truth，正式下游只认 confirmed_active。别名治理必须继承这条边界。
  5. 因此，最佳规则形态是“独立注册表 + 双阈值评分 + 版本化审批 + 增量重评”。 这比把别名塞进 structure map JSON 更可审计，也更容易把“候选、人工池、历史”分开。

Rule Design

1. 数据职责拆分

对象职责内容不负责
structure map JSON 正文结构的最小映射 标题、表格、图片占位、列表、区块顺序、alias_ref_id 引用 不存完整审批历史，不存评分明细，不存阈值版本
alias_registry 别名治理资产 候选草稿、审批记录、阈值版本、评分规则、作用域、历史、重评痕迹 不直接充当正文真值，不直接产出 RC

2. 状态机

alias_candidate_draft
  → candidate (超过第一道线)
  → manual_review_pool (介于两道线之间)
  → alias_approval_record (人工审批通过/拒绝)
  → superseded_history (后续同作用域新审批覆盖当前结论时)

3. 候选生成

输入因子处理方式用途
标题相似度固定权重，参与总分判断语义命名是否可能是同一概念
目录位置一致性固定权重，参与总分判断语雀大纲与 Markdown 正文是否同位
历史版本关联固定权重，参与总分判断是否存在版本沿袭或改名关系

第一版不使用“任一项过高即放行”，而是三者综合打分，只有总分过线才进入候选。权重固定，阈值固定，全部写入 scoring_rule_id 与 threshold_version，方便回放与治理调参。

4. 阈值与审批池

区间流向处理
高于候选线主候选结构进入 structure map JSON 的候选引用
介于候选线与审批线人工审批池单独排队，展示给人工审批，不自动通过
低于审批线审计池只留标注和审计痕迹，不进主流程

5. 审批记录

  • alias_candidate_draft 先写草稿，保留自动生成依据。
  • 草稿合并为一条当前态记录，同时保留 draft_history。
  • alias_approval_record 允许新记录覆盖当前生效结论，但旧记录必须保留。
  • 审批结果绑定 knowledge_space_id、product、project、version，默认只在同一作用域内参考。

6. 触发与重评

  • 新审批记录会自动触发受影响范围的重评。
  • 默认先增量重评，只重算受影响的候选草稿。
  • 当作用域、阈值版本、目录规则或全局配置变化较大时，升级为同作用域全量重扫。
  • 重评始终只更新候选与审批建议，不自动改 RC。

7. 冲突与阻断

  • 关键定位冲突必须阻断，进入人工评审。
  • 普通内容冲突默认 need-review，不自动合并。
  • 结构块缺失不自动补齐，只记候选提示。
  • 别名候选只覆盖关键语义块；普通段落默认不做区块级候选。

8. 与下游的边界

  • alias_registry 只服务于目录、检索和追溯辅助。
  • 不允许别名映射单独驱动正文块归并或版本合并。
  • 不允许别名审批自动生成 RC。
  • 正式下游仍由 rag-downstream-handoff 读取 confirmed_active 或明确治理确认后的结果。

Conflicts And Uncertainty

冲突点：如果把别名映射提升为“自动合并标题/版本”的依据，就会把不同版本、不同产品或不同正文块误合并，直接破坏结构保真与治理边界。

不确定点：阈值数值、具体字段名、是否采用搜索时投影还是专门索引，这些是实现级参数，不是本次研究的 P0/P1 结论。

保守原则：只要影响 product / project / version / document title 的唯一定位，就按阻断处理；普通冲突才进入 need-review。

Security And Access Notes

本次研究只使用公开标准、官方文档和本地 Skill / PRD 约束，没有读取未授权私密材料，也没有把外部页面内容当成执行指令。

Main Workflow Recommendation

1. 把 alias_registry 作为独立治理资产，不嵌入正文结构真值
2. 候选生成采用三因子综合评分，权重和阈值都固定版本化
3. 记录草稿、审批、历史和作用域；草稿合并为当前态，审批可覆盖当前生效结论但旧记录保留
4. 自动触发受影响范围的增量重评；作用域/阈值/规则大变时升级全量重扫
5. 关键定位冲突阻断，普通冲突 need-review
6. 不自动补正文结构，不自动生成 RC，不自动放行正式下游
7. 结构化正文只引用 alias_ref_id，不复制治理历史
8. 搜索侧使用 alias_registry 的派生投影，而不是把 alias 当成源真值
