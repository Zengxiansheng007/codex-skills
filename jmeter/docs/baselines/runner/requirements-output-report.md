# jmeter-tps-runner：目录准备与独立报告需求

目标项目：`work/jmeter-workbuddy-development-20260921`。本文是本轮需求增量，与历史 [实施需求 v0.3.1](requirements-v0.3.1.md) 配合阅读；不覆盖历史文件，不表示 Skill 包已经升级。

用户已确认 R1–R10 的业务选择，并在 R11-Q15 确认共同理解、结束本轮 Grill、保存需求。**用户于2026-10-14在R12确认本文实际保存版本v0.1及配套术语表**，真实答复为“确认当前 v0.1（推荐）”，来源为<会话答复引用>。本次仅补记确认状态与依据，需求／验收内容及版本不变；新增功能尚未实现或经过真实 WorkBuddy 验收。

## 1. 背景与目标

工程师希望首次确定压测产物根目录后，后续任务自动按标准结构保存报告、原始结果和执行副本，避免手动建目录及路径分散。

原 runner 将采样与 Dashboard 生成合并在一条命令中。用户遇到500并发、约74%错误率时，报告十多分钟仍未生成，难以区分采样是否结束、报告是否仍在处理和是否需要停止等待。现有材料不足以确认根因或估算生成分钟数。

本次目标是分开记录与控制采样、报告生成和等待处理：保留完整 JTL，每档单独生成官方 report，报告核验后继续寻峰；长等待由监控通知 WorkBuddy，WorkBuddy 分析并由用户决定是否停止。**拆分本身不承诺提速或修复此前卡住的根因。**

## 2. 角色、范围与继承规则

| 角色 | 本次职责 |
|---|---|
| 测试工程师 | 首次确认存储根；确认正式任务；根据 WorkBuddy 的分析决定继续等待或停止，必要时参与人工退出核查。 |
| WorkBuddy | 调用固定入口，建立并关联真实后台任务；收到监控通知后复核、续建监控、只读分析并询问用户；解释和交付实际结果。 |
| 固定压测程序 | 强制准备目录，串行调度采样／报告，保存真实阶段及结果；仅按用户决定控制原报告，核实退出后推进。 |
| 监控程序 | 覆盖本次任务的各轮报告，观察报告阶段及等待时长；达到提醒条件时只通知 WorkBuddy并退出。 |
| JMeter 5.6.3 | 执行已确认副本的采样；使用同轮结果单独生成官方 Dashboard。 |

本次包括目录准备、采样／报告分离、任务级后台监控、WorkBuddy 分析与人工报告停止，以及对应交付状态。

既有业务规则继续适用：原 JMX 只读，固定程序仅改变正式运行副本的目标并发及 HTTP 请求启用状态；每轮只执行当前目标及已确认必要前置，逐目标串行。起始候选来自现有配置、上限由工程师确认；预设并发50／100／200／500是绝对档位、每任务确认。每目标最多6轮，相邻粗测 TPS 下降≥3%或质量不合格时按既定规则转细测；首轮不合格按原规则结束该目标。质量门槛每任务确认，原候选值为错误率≤0.5%、P90≤2500ms。细测、预算、对齐10、不重复档位及不自动复测保持原规则。

本次不包含 JTL 派生 TPS／P90 替代程序、自动重发压测、自动补生成报告、自动硬等待上限、自动停止卡住进程、JVM 调参、诊断工具安装或分布式压测。writer 的编写与1线程／Ramp-up 0／1秒短验证职责不扩展到正式寻峰。新接口和实现方式进入后续规格阶段。

## 3. 标准产物结构

层级沿用“HTTP 请求名称／并发数／report、result、plans”，在其外增加唯一任务目录：

```text
<首次确认的根目录>/
  <自动创建的唯一任务目录>/
    <HTTP请求名称及必要身份后缀>/
      <本轮实际并发数>/
        report/<本轮独立报告目录>/
        result/<各轮JTL、采样日志、报告生成日志>/
        plans/<各轮JMX执行副本>/
    <本任务配置、状态、事件、问题及汇总产物>
```

该示例说明目录关系，不给出真实根路径、任务名或本次执行配置。具体文件名和状态接口由后续规格定义，须保留轮次隔离。不同任务可以测试同一请求及相同并发，但不能覆盖彼此结果。未实际选择的并发档位不预先批量建空目录。报告输出位置须满足官方空目录条件。

## 5. 流程与异常表现

### 5.1 正常一轮

已确认任务 → 选出当前目标／并发 → **固定前置脚本准备本轮目录** → 生成并校验允许变更的 JMX副本 → **采样** → 保存退出及JTL → **独立生成官方report** → 真实结束及产物核验 → 读取目标官方指标 → 按既有算法继续／细测／结束当前目标。

官方命令的概念形式为：

```text
jmeter -n -t <本轮副本.jmx> -l <本轮结果.jtl> -j <采样日志>
jmeter -g <同轮结果.jtl> -o <本轮空报告目录> -j <报告生成日志>
```

这是方案表达，未执行命令。Windows `.bat` 的安全参数传递、实际入口及生效的保存／报告配置须在后续设计保持并验证；不能因 .jtl 扩展名而假定内容满足官方 CSV输入要求。report核验继续检查现有必需产物（statistics.json、index.html、content/js/dashboard.js）、目标行与官方字段。

### 5.2 长等待与通知

报告满10分钟未完成 → 监控保存一次提醒并退出 → WorkBuddy 收到原生后台完成通知 → 复核身份与当前状态 → 主任务仍活动时先续建监控 → WorkBuddy 分析 → 说明结论／不确定性，请用户选择。

用户未答复时，报告仍可运行并自然完成。新监控继续观察同一报告及后续报告，但不再次发送同报告的长等待提醒。明确新异常可交接事实，不能将旧等待换名重报。10分钟是提醒条件，不是官方耗时基准、死锁证明或自动停止时限。

### 5.3 用户选择停止

用户对原报告明确选择停止 → 固定控制入口重新核对身份与当前阶段 → 对该报告执行停止并核实真实退出 → 标记本轮报告未完成／已停止，结束该 HTTP寻峰 → 保留此前有效候选 → 执行下一个 HTTP请求。

如果停止无法完成或退出未知，后续发压等待人工核查。核实退出后继续下一目标。主执行、报告与监控之间的进程归属必须能实现“监控退出不终止报告、报告停止不终止主调度”；具体实现不在本文提前选定。

### 5.4 其他异常与边界

| 情况 | 预期行为 |
|---|---|
| 根目录失效、目录准备失败、已有产物占用 | 说明失败，不启动该轮，不静默清空、迁移、覆盖或选择新根。 |
| 报告进程结束但必需产物缺失／不可读 | 报告技术失败，不等待至10分钟才承认失败；按既有目标技术问题策略处理，不补造指标。 |
| 报告有部分文件，但生成尚未真实完成 | 不当作可评分的完整report；窗口从原报告开始计时。 |
| 报告在通知或答复到达前自然结束 | 重新核对旧报告并标明已结束；旧停止不作用于当前新轮次。 |
| WorkBuddy缺诊断工具／无法附加 | 说明分析局限，不自动安装、不直接认定卡死，仍请用户决定。 |
| WorkBuddy正等待首个问题答复 | 后续通知／完成展示可能延迟，后台程序可继续；答复后重新读取最新状态，沿用已接受边界。 |
| 主任务已经终态 | 监控结束，WorkBuddy不为旧告警无条件续建。 |

## 6. 非功能要求与已确认取舍

- 首期范围为 WorkBuddy＋Windows＋JMeter5.6.3，保留既有 Python3.11+运行边界。宿主后台／输出／提问工具以真实会话 schema为准，不假设 Goal模式或直接消息推送API。
- 中文／空格路径、独占输出、源JMX哈希及副本差异校验、必要摘要与本地交付沿用原要求。诊断摘要不抄录Cookie、账号凭据或完整敏感响应。
- 监控保存提醒后自行退出，通过真实后台任务完成回执交接；停止监控不应将报告变成其被终止的子任务，报告停止也不应杀掉主调度。
- CPU活动、静默日志、短时无文件变化都可能存在多种解释。WorkBuddy依据实际证据表述有活动／疑似异常／证据不足，不输出未经证明的剩余时间或“已经卡死”。
- 选择等待官方report后评分，保留权威口径，接受Dashboard生成仍可能耗时。此次没有引入轻量统计器。
- 选择任务级监控与先续建再提问，减少普通轮次的模型参与；用户接受阻塞问答时通知可能延迟。现阶段不承诺通知即时到达或全程无监控空窗。
- 用户选择10分钟单次提醒，并保留人工停止决定；没有自动硬停止上限。用户选择等待核实退出后继续，故停止失败时可以需要人工处理。
- 本轮未设报告性能SLA、固定诊断采样频率或诊断线程快照次数。它们不能被实现者自行解释为已确认业务阈值；必要的技术参数在后续设计说明依据。
