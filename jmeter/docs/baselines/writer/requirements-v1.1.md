## 背景与目标

测试工程师在浏览器抓取待测接口，将复制的cURL Bash交给WorkBuddy，得到能被JMeter执行、能交给指定jmeter-tps-runner使用的JMX。已有JMX也可交给writer做有限试跑，减少正式寻峰前的脚本执行、认证和输入兼容问题。

writer只负责脚本编写与短验证。正式并发选择、质量门槛、TPS寻峰、逐接口正式压测及性能汇总继续由runner负责。本次不新增一套寻峰控制器。

两个核心场景：

1. 从单条或多条业务cURL编写JMX，配置请求头、默认断言及需要的Cookie读取/登录准备逻辑。
2. 从已有JMX执行有限试跑，保留原件与既有业务规则，如实报告执行、认证/断言及指定runner的接收结果。

## 输入与任务参数

### 新脚本

工程师提供业务cURL和接口名称；名称缺失时writer可拟定稳定、可区分的名称并在交付中列出。方法、URL、query、静态头及正文以cURL为依据，不根据请求名称猜测业务内容。

正式Ramp-up与持续时间在创建时由工程师提供，writer写入交接原件。writer不自行填入历史任务的120秒/180秒，也不自行建议正式并发区间。

需要登录自动准备Cookie时，输入须足以表达登录请求及账号参数。仅有一个URL、但无法判断方法/正文/账号字段时，补齐必要信息。已有响应样例/路径足够时直接编写；缺少Cookie提取依据时按Q17进行一次预登录。

### 已有脚本

提供JMX及实际需要的外部文件、目标HTTP请求和必要前置信息。writer先读取计划；疑似认证/前置、依赖或Cookie用途无法确定时补问。原件及原始输入数据保留，不因短试跑改写业务断言或正式时长。

### 每次验证

确定实际目标环境、JMeter入口、输出目录、指定runner来源/版本、目标与前置、会话模式和一个验证账号/会话。没有Cookie需求时不要求登录账号。需要用户填写的CSV尚无有效内容时，交付待填模板，认证验证保留为未完成。

本节描述未来执行任务所需输入；当前对话没有提供或执行任何新的业务验证任务。

## 请求编写规则

### cURL转换

- 收到的Bash作为数据解析，不执行原始命令、不使用eval。
- 保留方法、URL/query及重复参数、正文类型/内容、必要编码、静态头的实际语义。
- 检出不支持或不能保真的选项、文件依赖、Shell构造时说明具体内容，不静默删除后声称等价。
- cURL里保留的其他认证不自动转换为Cookie；已有Bearer/Basic/业务签名按实际请求处理。
- 支持文本请求正文不等于默认断言支持任意文本响应；新业务请求仍按已确认的success=true规则，特殊要求由工程师主动提出。
- 不借用其他转换器的默认200断言、默认时长或默认账号模型替代本次规则。

### HTTP请求头

组级共享Header Manager只存Cookie等需要更新的值；其他静态头留在对应请求，保持cURL设置。Cookie变量只应用到确需复现Cookie使用的请求，不能因位于同一JMX而给全部请求添加Cookie。

需要参数化Cookie的请求，应避免子级捕获旧Cookie覆盖组级动态值。原生组件的作用域与最终有效值须可核对；不同时引入第二套自动Cookie来源覆盖CSV值。

不统一新增Accept、Content-Type、User-Agent、Origin或Referer。JMeter实现必需的转换，例如请求实现自行计算Content-Length，应说明差异；不承诺不能兑现的逐字头部复现。已有JMX的头配置不自动重写，发现问题时说明。

### 业务断言

新业务HTTP请求默认使用响应JSON的`$.success`与期望值`true`进行断言，特殊规则由工程师主动提出，不逐请求追问业务成功标准。

这是响应验证，不能将SampleResult.success强行置为true。false、缺字段或无法解析JSON应按默认组件规则判失败；具体组件实现及类型边界由后续规格与测试核对，不自行扩大严格类型规则。

已有JMX：

- 保留已有断言及其业务语义，不自动替换为success=true。
- 缺少业务断言时只提醒，不阻塞试跑和后续交接。
- 已有断言真实失败时仍按验证失败处理，不能将“缺断言提醒”的例外用于忽略失败。
- 无业务断言时只记录“业务断言未验证”，不能因HTTP成功写成“业务正确性已通过”。

## Cookie与认证流程

### 判断规则

| 输入证据 | writer行为 |
|---|---|
| 提供足够的登录接口和账号材料 | 自动认证路径；需要时一次预登录，编写同JMX的setUp与CSV流程。 |
| 没有完整登录材料，但cURL/规范有Cookie使用证据 | 生成手填CSV与原生读取、Cookie变量及适用请求引用。 |
| 明确采用其他认证，无Cookie使用依据 | 保留原认证，不自动添加Cookie路径。 |
| 无法判断Cookie需求或名称/字段映射 | 标记不确定，只补问必要信息；不猜测。 |

cURL携带Cookie只能证明捕获请求使用了Cookie，不等于已证明认证必需；401/403也不是自动选择Cookie的依据。[判断研究](research-cookie-need-detection.md)

### 一次预登录

已有充分响应材料/字段路径时不额外调用。缺少提取依据时，用一个验证账号调用登录接口一次，读取实际JSON，确定字段与Cookie头的对应关系。

如果响应给出完整Cookie头值，按该值引用；若只给裸会话值，还需要对应的Cookie名称。没有依据时不把任意token拼成Cookie，不猜通用`$.data.cookie`路径。

预登录用于生成前获取材料；完整JMX试跑会另行执行其认证逻辑。两阶段分别计数、分别保存结论。预登录失败时停止并给建议，不自动再登录。

### 手工Cookie

writer生成待填写的cookie.csv和官方CSV Data Set Config，配置Cookie变量并应用到相应请求。CSV实际Cookie由工程师填写和在正式任务前更新；空模板、占位内容或抓包旧值不能冒充本次有效认证。

没有有效Cookie时仍可交付脚本和模板，但不报认证验证通过，也不伪造已完成的试跑。

### 自动Cookie

同一JMX内，setUp登录HTTP请求→原生JSON提取→必要有效性检查→受控CSV保存；标准业务组使用原生CSV Data Set读取，动态Header引用Cookie变量。

CSV落盘并非JSON提取器的原生能力，需由writer生成有限、可核对的固定保存构件。正式执行由JMeter承担，writer不在正式每轮运行时介入。

正式自动模式每轮重新准备并发布全部配置账号的Cookie CSV。认证准备失败或输出不完整时不能冒充本轮成功、不能自动回退旧CSV。具体构件、发布方式及必要消费者证据在后续规格中确定，不因此增建writer正式控制器。

### 原生CSV使用

- writer新生成的Cookie CSV读取配置已确认Recycle on EOF=true：末行后回到首条数据继续读；表头不能被当成Cookie。
- Stop thread on EOF=false、Sharing Mode=All threads按原生默认显式记录，为实现默认，不附加永久线程身份保证。
- JMeter按主迭代读取并赋值；多账号模式不保证同一线程始终对应同一账号。
- 循环复用文件内容不等于重新登录或延长Cookie有效期；每轮自动刷新由setUp流程负责。
- 单账号短验证必须实际只使用所选验证会话；不能读取全部账号后仅在报告中声称验证了一个。
- 既有JMX的CSV读取配置按实际保留并报告，不假定所有现存CSV实例必然循环；Q22仅增加认证CSV文件引用的副本权限，不自动改写其列名、编码、共享或EOF策略。

## 短验证与副本契约

### 固定配置

| 项目 | 短验证配置 |
|---|---|
| 业务线程数 | 1 |
| Ramp-up | 0秒 |
| 调度持续时间 | 1秒，启用调度 |
| 目标选择 | 逐个HTTP目标；保留其实际必要的已确认前置 |
| 自动认证覆盖 | 一个验证账号 |
| 重试 | 不自动重试 |

1秒是业务线程组的持续时间配置，不是整个JMeter命令的墙钟上限，也不强杀在途请求。启动、setUp及处理结果会增加总用时；1秒内可能有多次快速请求。

多账号正式JMX的账号规模不因试跑而被改为一个。验证副本只覆盖一个账号，结果不能声称其他账号的凭据/会话已验证。

### 已确认的可改项

固定程序仅在验证副本中调整线程数、Ramp-up、循环/持续时间/调度、启用集合，以及为单账号隔离所需的认证CSV文件引用，使实际试跑满足1/0/1和一个验证账号。保留原JMX、正式配置、业务断言与原始数据文件。副本差异应列出字段、原引用和验证引用；其他业务参数或非认证文件引用不因此获得修改权限。

副本启用当前目标及确需的认证/前置，关闭本轮无关HTTP请求。要检查实际样本覆盖，不能把JMeter退出0或目标被启用当作已执行。

### 已确认的验证CSV隔离（Q22）

在既有JMX直接引用多行Cookie CSV、且1秒内多次迭代时，原生CSV会逐次取行。单线程不等于只使用一个账号。

用户Q22选择A：允许固定程序创建单账号/单Cookie验证CSV，并仅在验证副本中替换对应认证CSV的文件引用；保持原JMX、原CSV和正式交接配置不变。验证CSV沿用对应输入的列/变量格式，保持原生CSV读取，不新增身份分配器，不改runner正式副本白名单。

这一补充仅用于有限试跑的数据隔离，不允许覆盖原文件或改写无关业务逻辑。必要引用无法识别时说明缺项，不盲目替换全部文件路径；不能以限制为一次循环替代已确认的持续时间验证，或实际使用多个账号却只记录一个。

## 验证结论与正常/异常流程

三层分别记录：

| 层 | 核对内容 | 结论边界 |
|---|---|---|
| 脚本执行 | 实际运行结束、目标样本、日志/结果可读、必要输入可用 | 启动成功或exit0不能代替目标实际执行。 |
| 认证与已配置断言 | 需要的Cookie/登录/导出/读取、已存在断言及新计划默认断言 | 只覆盖所选验证账号和实际样本；既有缺业务断言记提醒。 |
| runner消费者 | 指定runner的实际版本/位置、目标/前置、组件与文件依赖可接收 | 没有消费者核验不能说兼容；候选源码不等于同事安装版本。 |

交付结果区分：

- **可交接**：适用的必需检查通过，真实执行范围明确。
- **可交接（有提醒）**：其他必需检查通过，但已有JMX缺业务断言；允许继续，明确业务断言未验证。
- **失败**：预登录/试跑/认证/已配置断言实际失败，或消费者明确拒绝；停止验证，给出原因和建议，不自动重试。
- **待补充/未验证**：必要材料不足、未实际覆盖目标或某层尚未核验；记录事实，不冒充通过。

缺业务断言只提醒，是Q21对旧“三层全满足”表述的明确例外；不扩大为所有依赖、认证或兼容问题都不阻塞。

### 正常流程

1. 读取cURL/JMX和依赖；确认目标、正式参数、会话模式及指定runner。
2. 根据材料选择无需Cookie、手工CSV或自动登录；只有不确定时补问。
3. 自动路径需要时预登录一次，取得实际提取依据；编写请求、头、默认断言、认证与CSV逻辑。
4. 原件及依赖静态核对；调用固定验证程序准备逐目标副本。
5. 一个验证账号、业务1/0/1执行；JMeter原生读取/分配CSV。
6. 读取实际退出、目标样本、认证/断言结果及消费者结论；已有缺业务断言只给提醒。
7. 交付最终JMX、所需文件/说明、实际验证范围和下一步；正式任务独立调用runner。

### 异常与恢复

- 必要输入/路径/认证映射不明：先完成可独立的编写工作，列出缺项；依赖该材料的验证不虚报通过。
- 不支持或不能保真的cURL内容：说明具体内容与差异，不静默丢弃。
- 登录失败、Cookie提取缺值、CSV导出/读取失败、实际断言失败：停止本次验证，输出证据支持的原因与修改建议。
- 没有目标样本：标记该目标未验证并说明实际情况，不以exit0替代。
- 已有脚本没有业务断言：继续允许的流程，交付提醒。
- runner拒绝：如实报告兼容失败和必要适配，不因JMeter能运行就改写结论。
- 用户修正材料/脚本后可明确发起新的任务；不自动续跑、换名重试或放宽断言。
- 超时/中断的专门机制不在本方案；由Agent在遇到时自行处理。真实结束或处理结果无法核实时，不将未知状态写成验证完成。

## 验收条件（未来验证目标）

### AC-001 / REQ-001：转换正确性

给定首期支持的HTTP(S) cURL，生成JMX后逐请求核对method、URL/query、头与正文，包含常见引号、中文、重复参数和所支持正文类型。必要引擎转换有记录；不支持输入有具体说明，不执行收到的Bash、不静默丢弃后报保真。验证方式：结构检查、转换样例对照与受控接口回显。

### AC-002 / REQ-002：Cookie判断及手工路径

分别给定已有Cookie使用、明确其他认证和不确定材料，行为符合判断表。手工模板与CSVDataSet/变量/头引用一致，仅在需要的请求生效；未填写有效Cookie时不能报认证通过。EOF循环、表头及引号按原生配置验证，不附加固定账号承诺。验证方式：生成物检查、CSV读取及实际请求对照。

### AC-003 / REQ-003：自动认证与账号范围

充分材料不额外预登录；缺少时一个账号一次预登录，真实响应确定路径与Cookie名称。JMX同文件认证先完成、输出CSV可读后业务消费。正常、缺值及导出失败区分；失败不假成功、不自动回退旧数据、不重试。短验证只覆盖所选账号，正式计划仍保留全部配置账号的准备逻辑。验证方式：固定模板审查、本地受控登录响应与文件证据；多账号准备逻辑用受控样例验证，不据单账号实测宣称全账号有效。

### AC-004 / REQ-004：有限试跑及原件保留

新生成/已有JMX按逐目标1/0/1配置试跑，启用当前目标和必要前置，实际样本存在、退出及原始结果可核对。需要CSV隔离时，固定程序生成单账号验证数据，仅在验证副本中替换对应认证CSV引用，原件/原始CSV/正式交接配置保持不变；列格式/变量匹配，循环内实际仅使用所选会话，差异可核对。失败停止，输出原因/建议、已测/未测范围，无自动重试。专门超时/进程树停止机制不作为本次验收项。

### AC-005 / REQ-005：头与断言

新业务请求默认`$.success`期望true，false/缺字段/非JSON等按默认组件规则失败，不能强置SampleResult成功。静态头保留cURL，动态Cookie不会被旧同名头覆盖且只进入适用请求。已有断言保持；已有缺业务断言只提醒、不阻塞。验证方式：生成物及实际有效头、正常/业务失败响应样例对照。

### AC-006 / REQ-006：分层交付

交付原件/依赖/说明及实际证据位置，正式Ramp-up与时长使用工程师输入，短验证配置不回写。三层结论分别有来源、实际账号/样本范围可见。已有缺断言时允许“可交接（有提醒）”，但业务断言记录未验证；真实其他失败或未验证不冒充就绪。指定runner被拒绝/未知时结论如实。验证方式：人工审阅与证据/消费者检查对照。

### AC-007 / REQ-007：最小消费者兼容

受支持的自动认证、手工CSV及无Cookie新计划能由指定runner正确接收；当前业务目标、必要认证/前置精确启用，不启用无关业务请求。登录样本不混入目标业务Statistics；固定CSV保存构件与生成依赖有资格，未任意放行脚本。关联回归证明旧计划、寻峰决策、正式副本允许变更范围和源文件保留约束不回退。验证方式：变更审查、限定消费者测试和本地受控集成。本项是后续开发目标，当前没有通过证据。
