# jmeter-tps-writer — 规格 v0.1

日期：2026-10-13。阶段：独立 to-spec；本轮仅编写规格，不开发、不运行 JMeter、不安装或发布。

输入：完整需求 v1.1（整份仍待确认，核心 Q1–Q22 已有答复）、六场景 Logic 原型、现有 runner 候选源码与测试、JMeter 5.6.3 随发行包附带的官方文档。原型没有真实运行证据，候选不等于同事电脑的安装版本。

本轮用户已确认测试边界：“采用入口行为测试＋受控 JMeter 集成（推荐）”。这不自动授权当前运行真实 JMeter，也不追记为整份需求或规格的确认。

## Problem Statement

工程师已经能从网页取得待测接口的 cURL，但仍需手工创建 JMX、设置请求头和断言、处理 Cookie，并在正式寻峰前排查脚本、认证及 runner 接收问题。把这些工作直接交给 runner，会混淆“脚本是否正确”和“在质量约束下哪档并发更好”。

现有 runner 已具备逐请求寻峰和官方报告处理能力，却尚未接收同 JMX 的 setUp 认证与固定 Cookie CSV 保存结构。单线程验证也不能自然保证只使用一个账号：原生 CSV 会按迭代继续读行。

## Solution

新增 WorkBuddy 使用的 jmeter-tps-writer，从 cURL 编写原生 JMX，或检查已有 JMX；通过固定入口准备独立副本，逐目标按业务 1 线程、Ramp-up 0、持续 1 秒进行有限验证。需要 Cookie 时，采用工程师手填 CSV，或同 JMX 的 setUp 登录、JSON 提取、固定 CSV 发布与原生 CSV 消费。

正式配置、原件与原始数据保留。writer 交付 JMX、必要依赖、证据与分层结论；runner 重新确认正式任务后独立执行寻峰。只补 runner 的必要消费者适配，保留寻峰规则、官方指标和宿主执行机制。

## Implementation Decisions

以下为可审阅的技术设计；不冒充现有实现。接口字段、准确改动位置及资格门见配套文档。

### 1. 两个独立 Skill，一个清楚的交接边界

writer 提供分析、编写、必要的一次预登录、有限验证及交付入口。runner 提供无发压的消费者接收检查，并继续使用现有正式入口。writer 不在正式每轮被调用，不建立第二套正式控制器。

Python 3.11+ 标准库承担任务数据、XML、副本、证据与命令编排。cURL 解析优先用本机 JMeter 5.6.3 的公开解析器，由小型本地适配器映射原生 JMX；既有 JMX 不经 cURL 重建。适配器的无头使用和支持语法必须先通过资格验证，不能宣称存在官方无头转换命令。

### 2. 输入与交付接口显式分开

输入任务有来源类型、待测请求、正式参数、会话模式、认证材料、一个验证会话、指定消费者及本次验证确认。秘密值留在本地输入，不作为可分享元数据。

编写返回正式 JMX、依赖描述、角色关系及转换差异；验证返回逐目标三层结论、实际证据及总体交接状态。编写成功不代表验证完成。runner 不接收 writer 的 1 秒副本作正式计划，也不继承 writer 的短验证授权。

### 3. Cookie 和断言按已经确认的规则编写

手工 Cookie 与自动 JSON Cookie 分支由实际材料决定；不确定才补问。Cookie 头的名称/字段映射必须有来源，不把任意 token 当 Cookie，不使用第二套 Cookie 来源覆盖 CSV。

新业务采用原生 JSONPath 断言，期望 true，沿用组件语义；已有计划保留断言，缺断言只提醒。认证不能仅凭 HTTP 200 或 JSON 提取器有默认值判成功。

### 4. 认证结构限定为可核对的模板

新自动计划使用原生 setUp 认证组、标准业务组、原生账号 CSV、JSON 提取器及固定 Groovy 前/后处理构件。首期认证顺序使用一个认证线程和明确账号循环数；短验证副本循环数为一个账号，正式原件仍为全部配置账号。

固定构件附着在认证 HTTP 下，随该 HTTP 的启用状态生效，避免为了启停辅助采样器扩大正式副本变更白名单。只资格确定模板、参数和绑定，不将任意 JSR223 加入安全集合。现有不符合此契约的认证结构保留原件并报告兼容缺项。

认证失败通过 JMeter 计划内的错误语义停止依赖业务；这属于认证正确性，不新增整体超时、OS 进程树强停或自动取消模块。

### 5. 本轮生成依赖与已有文件分别核验

手工 Cookie / 账号输入必须在执行前存在且满足原生列格式；自动生成的 Cookie 是本轮产物，启动前不要求旧文件存在。

提议让固定认证构件依据执行 JMX 的目录和文件名定位本轮 Cookie 与认证证据，并通过进程内已声明属性发布给业务原生 CSV。这解决副本迁移与重复目录下的轮次隔离，正式 runner 不改写 JMX 的 CSV 路径。

只允许这一限定生成依赖表达式，不放开一般动态文件或相对路径规则。实际文件基准、属性解析时机及无关线程组不消费产物，必须由受控 JMeter 资格测试证明；不成功则修订实现方案，不放宽白名单冒充通过。

### 6. 验证副本契约独立维护

验证只允许目标业务组的线程、Ramp-up、循环/调度/时长、HTTP 启用，以及所选认证组必要的一账号循环配置和认证 CSV 文件引用隔离。CSV 的列、编码、EOF 与共享策略保留；业务参数、头、断言及原始数据不变。

副本生成后独立解析并比较，不能只信任生成器自己的差异清单。整体阶段未知不自动重发。实际验证失败后停止剩余验证，不按 runner 的“继续后续目标”规则继续试跑。

### 7. runner 增加限定消费者能力

新增认证角色与目标关联、受控构件资格、本轮生成依赖及认证证据核验。普通同组业务前置继续遵守原规则，认证角色不成为寻峰目标。

每轮完成后，先核认证证据与登录结果，再读取业务目标官方指标；认证失败归入本目标技术问题，不计合格峰值、不自动重发，后续目标沿用现有规则推进。已实际启动的轮次仍真实记录，不修改预算规则。

无自动认证元数据时保持旧路径；声明自动认证却缺契约时拒绝，不能隐式按普通计划降级。

### 8. 正式副本与寻峰规则保持

正式副本仍只允许当前标准业务组并发与 HTTP 启用变化。认证组配置、脚本、CSV 文件引用与业务断言不随并发变化。全局放开 setUp / JSR223 或变更任意路径不在本方案。

原有预设绝对并发、最多六轮、3% 相邻粗测下降触发、合格候选附近细测、质量门槛确认、官方指标选择、报告起止时间及问题队列规则保持。writer 不承诺找到全局容量上限。

## Testing Decisions

用户已确认：以公开入口行为测试及后续授权的受控 JMeter 集成为主。

- 主要边界：writer 的分析/编写/验证/交付入口，以及 runner 的只读接收入口与正式控制器入口。测最终产物、实际调用次数、样本、差异、启用集合和结论，不测内部函数调用顺序。
- 现有测试先例：runner 控制器可注入执行器及版本探针，已有合成报告/JTL、结构副本验证、无重试与源文件保留案例。优先沿用这些边界和夹具；writer 只增加固定单次执行适配的注入点。
- 真实 JMeter 不能被 fake 替代：setUp 时序、字段提取、固定 CSV 发布、动态属性解析、实际 CSV 行分配、有效请求头、断言及目标覆盖用本机 loopback 受控服务核对。
- 原生解析器、固定导出构件和目录解析先做技术资格门，再进入完整功能实现；不能凭文档或原型走通关闭资格。
- 原寻峰模块不修改。只跑关联的已有决策边界回归与新认证消费链；无关模块不全量重测。出现共享接口变更或真实失败再按影响扩大。
- WorkBuddy 的实际触发、脚本定位、路径与结论展示另外由真实宿主验证。第二环境暂无时保持未测试，不据本机结果声明同事环境通过。
- 完整未来用例及 REQ/AC 对应关系见测试方案。本轮所有产品测试状态为未执行；文档核对不等于软件通过。

## Out of Scope

- writer 正式寻峰、运行包装器、运行时钩子或复制 runner 核心。
- 修改粗测/细测、轮次预算、质量门槛或 TPS 指标来源。
- 上传、外部文件正文转换、复杂 Bash 执行、远程 cURL 转换服务、重型平台。
- 自研 CSV 分配、线程永久绑定账号、任意 JSR223 / 插件放行。
- 自动 Set-Cookie 采集替代 JSON 来源，猜测 token 到 Cookie 的映射。
- 已有脚本自动补写或改写断言；失败后自动修正、重试、延时或放宽断言。
- 专门整体超时、OS 进程树停止、宿主异步通知机制。本轮不新增它们的产品模块或验收门。
- 当前运行业务接口、真实 JMeter、安装、全局修改、远程发布、完整 PPT 或其他项目工作。
