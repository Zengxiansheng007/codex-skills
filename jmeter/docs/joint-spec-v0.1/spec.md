# jmeter-tps-writer / jmeter-tps-runner 联合规格 v0.1

日期：2026-10-14。状态：待审阅；本轮只制定规格、依赖与测试方案。原编号的命名空间保持：writer 使用 REQ / AC / DC，runner 使用 WB-FR / WB-AC；原文的 runner “AC-001”简写在联合映射中展开为 WB-AC-001，不与 writer AC-001 混同。

## Problem Statement

工程师从网页取得 cURL 后，仍需创建 JMX、处理请求头、断言与 Cookie，并验证能否交给 runner。已有 runner 在正式寻峰时把采样与 Dashboard 生成合在一个进程步骤，报告长等待会使采样状态、报告状态与是否可以继续混在一起。不同任务手动管理结果路径也容易出错。

writer 原规格与 runner 新增目录/报告需求相交于输入接收、认证、执行控制、存储及宿主桥接。若分开实施，两边可能分别修改同一接口，或继续同时遵守“process/storage 保持”和“必须拆分/强制准备”的冲突约束。打包源码还包含旧 candidate 没有的 Word 汇总与错误附录，直接复用旧候选会丢功能。

## Solution

在一个联合计划中保留两个 Skill：writer 负责 cURL→JMX、必要认证编写及 1/0/1 有限验证，交付正式原件及分层结论；runner 重新确认正式任务，负责目录、逐 HTTP 有界寻峰、每档独立官方报告、监控交接和汇总。它们通过版本化的计划/认证/消费者契约连接，分别维护副本权限与失败语义。

runner 首次确认固定输出根；每次自动创建唯一任务，实际选出的每轮先通过固定目录准备入口。采样与官方报告分开运行，报告完成核验后才决定下一档。独立监控覆盖任务内报告；每份报告生成满十分钟仍未完成，保存一次提醒并退出，由 WorkBuddy 原生完成机制接收。WorkBuddy 复核后先续建监控，再分析并让用户选择等待或停止。仅对原报告执行停止，核实退出后结束当前接口寻峰并继续后续接口。

## Implementation Decisions

以下是**本联合版本提出的设计**；业务依据来自现有已答需求，新增技术选择仍待整份评审与资格测试。

### 1. 一个计划，两个入口，消费者契约是连接点

writer 沿用分析、编写、必要的一次预登录、逐目标短验证与交付。runner 增加只读接收检查；正式运行仍经独立任务确认与固定控制器。writer 不调用正式寻峰来完成试跑；runner 不接收 1 秒验证副本作为正式原件。

认证模板/协议由 writer 持有生成职责，runner 持有受信模板与消费者解释器。两个包带相同版本的限定契约和模板摘要，不引入运行时相互导入或第三个常驻服务。消费者报告实际包标识、协议能力与接收结论；不存在对应入口的旧版本记不支持/未知，不假装已适配。

### 2. 保留 writer 编写规则和独立副本权限

收到的 cURL Bash 作为数据，优先薄适配本机 5.6.3 原生解析器；不支持内容明确列出。静态头保留到对应请求，共享默认头只放需要更新的内容；动态 Cookie 只对适用请求生效。新业务用原生 JSONPath 的 success=true 默认断言，沿用组件语义；已有断言保留，已有缺断言只提醒。

writer 短验证仅改独立副本的业务线程、Ramp-up、循环/调度/时长、HTTP 启用和必要的单账号认证 CSV 引用/认证迭代。原件、账号规模、原 CSV 及其他业务参数不变。1 秒是业务组持续时间，不是进程墙钟上限，也不保证只有一个样本。失败停止本次 writer 验证，不自动修正、重试或继续后续目标。

### 3. 自动认证由 JMeter 执行，runner 先核认证再评分

自动模式同一 JMX 内使用 setUp 登录、JSON 提取、限定固定保存构件与原生业务 CSV。正式每轮准备全部配置账号，writer 短验证实际只使用一个账号；JMeter 原生循环分配，不承诺永久线程身份。手工模式由工程师填写 Cookie CSV，空模板不能报通过。

沿用 AuthContract、逐轮 AuthenticationResult 和明确生成依赖。固定构件附在登录 HTTP 下，避免扩大正式副本的非 HTTP 启停权限。基于本轮计划定位生成 CSV、限定属性发布及非当前线程组行为列为 G-02 硬资格门，未实测不能报支持。

采样结束后，认证核验与官方报告生成是分别记录的检查。存在完整可报告 JTL 时按正常独立步骤生成报告，即使认证核验已失败；完成后不评分该轮，并结束当前目标继续后续。JTL 无法满足报告输入时直接记技术失败；报告未退出则仍沿用等待/停止与退出核查。**没有“认证失败后用 JTL 自算”或“用认证证据跳过官方报告等待”的分支。**

### 4. 固定根配置与强制目录准备

根位置首次由工程师确认，作为本机用户配置保存在 Skill 包之外。每次正式任务由固定入口排他创建唯一任务目录；每轮实际并发确定后调用同一目录准备脚本。返回绑定该任务/目标/轮次的路径清单与准备证据，执行入口缺此证据即拒绝。

目录按“唯一任务／HTTP 名及身份／实际并发／report、result、plans”。采样日志、报告日志、控制台、JMX、认证产物、状态与汇总均在根内；输入和根配置不是被复制/迁移的历史报告。准备失败按共享存储问题停止新轮，不静默换根或清空目录。

### 5. 正式轮次拆为两个官方执行阶段

保留安全 Windows 批处理参数边界。采样命令不合并报告；采样真实结束且结果可核后，用官方独立报告命令消费同轮 JTL。两阶段使用同一已确认运行环境和相容的保存/报告配置，分别记录身份、退出、日志和耗时。报告目录在启动时仍必须为空。

只有官方报告真正结束、必要产物和目标字段核验通过，且适用认证核验通过，才形成寻峰观测。每轮报告与下一轮发压串行。报告失败、停止或缺指标不填零，也不自动补生成或重新采样。

### 6. 主程序持有报告控制权，监控只读观察

主程序保存报告启动身份并持有报告进程组/句柄；监控作为 WorkBuddy 的另一个原生后台任务，只读阶段投影，写自己的提醒/退出资料。两个后台绑定分别保存，监控不拥有报告子进程，退出不影响报告。

每份报告从原始启动计满 600 秒后仍未完成，监控排他写入一次长等待记录，形成摘要后自行退出；续建沿用原提醒状态，不重置计时。普通报告结束和采样阶段由同一监控接续，不逐轮调用模型。主任务终态时监控正常结束，不发伪造长等待。

### 7. WorkBuddy 先续建，再分析与请用户选择

WorkBuddy 收到真实宿主完成通知后，读取交接摘要、最新主/报告状态及旧监控退出回执。只有旧监控确已结束且主任务仍活动，才建立一个新监控，然后只读分析本轮 JMeter。已有 JDK 工具可用时有限取证，缺工具不安装；十分钟、CPU 或日志静默均不是卡死证明。不确定也如实说明，让用户决定。

首个问题阻塞时后续通知、展示和下一次续建可能延迟，保留用户已接受的边界，不承诺即时推送或全程无监控空窗。通知入队、已展示、用户答复和执行控制分别记录；原 acknowledge 仍只是答复记录。

### 8. 报告专用停止必须通过主程序执行

用户明确选择停止后，固定控制入口提交绑定原报告的控制请求；主程序重新比对身份和当前阶段，再针对自己持有的报告进程范围执行。拟优先资格化 Windows 报告专用 Job Object 与进程句柄方案，主调度及监控不加入该报告 Job。创建归属、子进程继承和宿主嵌套限制属于 G-04，不能靠一个 PID 或 taskkill 成功回执跳过。

确认报告 Java/包装器均退出后，保存本轮未完成及停止原因，保留此前合格候选，结束当前 HTTP 并去下一请求。停止失败/退出未知进入等待核查，后续采样为零；主程序只做原身份的重新观察，不自动重启。迟到停止、重复请求和旧进程 PID 复用不能作用于新报告。

### 9. 正式寻峰、评分与汇总继续采用已有规则

绝对预设 50/100/200/500 由每次任务确认，不是增量步长；上限由工程师指定，每目标合计最多 6 次采样。相邻粗测 TPS 下降至少 3% 或质量超标按既定规则转最佳合格候选附近细测；首轮质量失败不下探。细测向下对齐 10、无重复、无自动复测。具体算法保持原消费者实现，不另写“联合算法”。

目标 TPS、P90、错误率、样本及起止时间来自官方 report；P90 按真实 90th pct 元数据定位，JTL 仅审计。报告/监控/控制活动不消耗新的采样轮次。保留 Word 汇总、结构化完整精度指标、实际轮次、并列候选及错误附录；增加阶段与搜索未完成说明，不把技术问题当质量不合格或绝对容量结论。

### 10. 共享改动只有一个实施顺序

后续在新的隔离候选中实施，以已核对打包源码为起点，对照历史 candidate，保留四处已有交付差异。统一顺序先冻结接口及目录/报告最小链，再 writer 编写/短验证、认证消费，随后监控与控制，最后关联验证及文档/包。共同修改控制器、桥接、预检的工作项串行合并。

旧“核心默认字节不变”和“保留 process/storage/桥接”仅在本次必要写集内被新要求覆盖。寻峰算法、质量门槛和正式 JMX 变更白名单仍保留；writer 的更大试跑权限不传递给 runner。

## Testing Decisions

用户已确认公开入口行为与受控集成的组合边界。优先复用原控制器的可注入执行器、版本探针、合成 report/JTL、独立副本比较和桥接证据核验。联合版本将执行器作为一个阶段化执行边界，避免为每个内部函数造测试入口。

- writer 测最终 JMX、有效头/断言、单账号实际使用、真实目标样本、三层结论与失败后调用次数。
- runner 测强制准备、采样/报告严格串行、认证先于评分、官方值、退出未知不推进及实际汇总。
- 监控/控制从固定公开入口测一次提醒、排他运行、续建顺序、准确停止、迟到/重复控制；可控时钟只证明逻辑。
- setUp、CSV、动态属性、官方独立报告、Windows Java 归属/退出及 WorkBuddy 原生通知/提问必须以真实受控证据补齐。600 秒缩时模拟不能代替真实时窗资格。
- 保留 G-01–03、W-01–18、R-01–12、J-01–08、H-01–05；原交接顺序相关案例按联合版本更新预期。新用例见测试方案及映射。每轮开发先跑新增模块与直接关联回归，有影响证据再扩测。

当前只执行文档结构/链接/编号/源保留核对，所有产品测试仍为 not-run，历史试验结果不追记为本次新能力通过。

## Out of Scope

- 合并两个 Skill 为一个入口、增加 writer 正式控制器或复制寻峰核心。
- 改变并发算法/预算/质量口径，以 JTL 自算替代官方 report，自动复测或自动补报告。
- writer 专门整体超时、进程树强停模块；runner 的报告专用控制不反向扩大到 writer。
- 任意 JSR223/动态路径放行、自动改既有断言/业务配置、自研账号分配器、永久线程身份。
- 自动硬停止报告、自动 JVM 调参、诊断工具安装、整任务重放/自动恢复或停止任意 Java。
- 解决没有原始证据的历史“500 并发/74%错误率”根因、承诺报告提速/耗时或证明全局峰值。
- 当前真实请求、JMeter 执行、WorkBuddy UI 导入、第二环境测试、安装、GitHub 发布以及改写历史文件/执行台账。
